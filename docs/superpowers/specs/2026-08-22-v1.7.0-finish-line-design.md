## Design rulings baked into this plan (defaults chosen; owner may override before execution)

1. **Splits carry category + amount + note only.** Attribution stays whole-transaction (per-card attribution is parent-level). A split's parts always sum exactly to the parent's `amount_cents`.
2. **Splits do not train the categorizer** — no Bayes learning, no rule creation from a split (no single merchant→category truth). Parent is stamped `categorization_source='manual'`; clearing splits re-runs the engine on the row.
2a. **A split transaction is categorized, by definition, and the engine must treat it as such** (ruling added 2026-08-22 after Task 2 review — my original wording in ruling 2 was wrong). Stamping `categorization_source='manual'` does NOT remove a row from `REVIEW_WHERE`, because that predicate's first disjunct is `category_id IS NULL` and a split deliberately leaves the parent's `category_id` alone. So both `REVIEW_WHERE` and `ELIGIBLE` in `src/lib/categorize/engine.ts` must additionally exclude any transaction that has splits. Without this: (a) a split uncategorized row nags in the review queue and the dashboard count forever, and (b) far worse, `rerunEngine` still considers it eligible and can flag it `is_transfer = 1`, which silently drops every one of its split parts out of every report and budget. Task 2b implements this.
3. **Undo import cascades over splits** (FK `ON DELETE CASCADE`) — owner ruled cascade-on-undo 2026-08-22.
4. **Rollover budgets carry positive leftovers only** (overspend does not create debt-carry), capped at 24 look-back months, per (scope, user, category), starting the month the toggle is enabled. Suggested-budget apply writes the BASE limit and its current-month-only guard is untouched.
5. **Annual budget targets are NOT built** — rollover covers the lumpy-expense need; YAGNI.
6. **Net worth = signed snapshot balances (assets +, credit cards − as SimpleFIN reports them) + manual snapshots for unlinked accounts − loan balances.** Accounts with no snapshot are excluded and the UI says so.
7. **Auto-sync cadence is user-selectable** (owner override 2026-08-22): every 6 hours, every 12 hours, daily, or weekly. Fires on the 5-minute tick when the last sync is older than the interval (with slack so cadence does not drift). A day whose SimpleFIN request budget is already spent skips silently — backpressure, not a failure.
8. **Upcoming bills v1 = items of kind subscription/contract with a billing cycle + amount set.** No merchant-pattern bill inference yet.
9. **No service worker / offline mode.** PWA scope is manifest + icons + installability only (LAN app).
10. **Monthly digest fires with the existing daily-slot machinery** in the first 3 days of a month, reporting the month just ended.

## Migration 0009 (single file, Task 1)

```sql
-- drizzle/0009_finish_line.sql

-- 1. Transaction splits. Sum-of-parts == parent amount_cents is enforced in the app
--    layer (single writer), not by CHECK: SQLite cannot express a cross-row sum CHECK.
CREATE TABLE `transaction_splits` (
  `id` integer PRIMARY KEY AUTOINCREMENT NOT NULL,
  `txn_id` integer NOT NULL REFERENCES `transactions`(`id`) ON DELETE CASCADE,
  `category_id` integer NOT NULL REFERENCES `categories`(`id`),
  `amount_cents` integer NOT NULL,
  `note` text,
  `created_at` text NOT NULL,
  CHECK (`amount_cents` <> 0)
);
CREATE INDEX `transaction_splits_txn_idx` ON `transaction_splits` (`txn_id`);
CREATE INDEX `transaction_splits_category_idx` ON `transaction_splits` (`category_id`);

-- 2. Balance snapshots (net worth history). One row per account per day; a later
--    write for the same day replaces the balance (upsert in the app layer).
CREATE TABLE `account_balance_snapshots` (
  `id` integer PRIMARY KEY AUTOINCREMENT NOT NULL,
  `account_id` integer NOT NULL REFERENCES `accounts`(`id`) ON DELETE CASCADE,
  `date` text NOT NULL,
  `balance_cents` integer NOT NULL,
  `source` text NOT NULL,
  `created_at` text NOT NULL,
  CHECK (`source` IN ('simplefin','manual'))
);
CREATE UNIQUE INDEX `account_balance_snapshots_uq` ON `account_balance_snapshots` (`account_id`, `date`);

-- 3. Rollover preference per (scope, user, category). Same expression-unique trick as
--    loan_matcher_rules_uq so household rows (user_id NULL) cannot duplicate.
CREATE TABLE `budget_rollover` (
  `id` integer PRIMARY KEY AUTOINCREMENT NOT NULL,
  `scope` text NOT NULL,
  `user_id` integer REFERENCES `users`(`id`),
  `category_id` integer NOT NULL REFERENCES `categories`(`id`),
  `start_month` text NOT NULL,
  `created_at` text NOT NULL,
  CHECK (`scope` IN ('household','personal')),
  CHECK ((`scope` = 'personal') = (`user_id` IS NOT NULL))
);
CREATE UNIQUE INDEX `budget_rollover_uq` ON `budget_rollover` (`scope`, coalesce(`user_id`, -1), `category_id`);

-- 4. Tax-relevant flag on categories (append column, ALTER TABLE convention).
ALTER TABLE `categories` ADD COLUMN `tax_relevant` integer NOT NULL DEFAULT 0;
```

A row's existence in `budget_rollover` means rollover is ON (delete = off) — same absence-is-off pattern as settings keys, no `enabled` column to drift.

Schema mirrors added to `src/db/schema.ts`: `transactionSplits`, `accountBalanceSnapshots`, `budgetRollover` tables and `taxRelevant` column declared LAST on `categories` with the standard ALTER-convention comment; CHECKs documented as SQL-only per house style.

New settings keys (no migration): `simplefin_auto_sync` (`'daily'`), `simplefin_auto_sync_user_id` (admin id used as `importedBy`).

New notification events (registry append, ids permanent): `sync_failed` (admin, immediate, default on), `monthly_digest` (all, daily_slot, default off).

### Task 2: Splits core library

**Files:**
- Create: `src/lib/splits.ts`
- Test: `tests/lib/splits.test.ts`

**Interfaces:**
- Consumes: `transactions`, `transactionSplits` from schema; `runEngine` from `@/lib/categorize/engine`; `nowIso` from `@/lib/clock`.
- Produces (exact signatures later tasks rely on):

```ts
export interface SplitPart { categoryId: number; amountCents: number; note?: string | null }
export interface SplitRow extends SplitPart { id: number; txnId: number }

/** Replaces all splits for a txn in ONE db transaction. Empty array clears splits. */
export function setTransactionSplits(input: { txnId: number; parts: SplitPart[]; userId: number }): void
export function getSplits(txnId: number): SplitRow[]
export function splitsForTransactions(txnIds: number[]): Map<number, SplitRow[]>

/**
 * The split-aware row source. LEFT JOIN transaction_splits: a txn with N splits
 * yields N rows carrying the split's category/amount; a txn with none yields one
 * row carrying its own. Every category aggregate consumes THIS instead of raw
 * transactions columns.
 */
export const EFFECTIVE_CATEGORY: SQL  // coalesce(transaction_splits.category_id, transactions.category_id)
export const EFFECTIVE_AMOUNT: SQL    // coalesce(transaction_splits.amount_cents, transactions.amount_cents)
```

Implementation notes (binding):
- `setTransactionSplits` validation: at least 2 parts (or 0 to clear); every `amountCents` non-zero, same sign as parent; parts sum EXACTLY to parent `amount_cents` (throw with the difference in the message); parent must exist, must not be a transfer (`isTransfer` → throw `'Transfers cannot be split.'`); every categoryId must exist and not be archived.
- On set (non-empty): delete old split rows, insert new, stamp parent `categorization_source = 'manual'`, `updated_at = nowIso()`. Parent `category_id` is left untouched.
- On clear: delete rows; if parent `category_id` is NULL, reset `categorization_source = 'none'` and call `runEngine([txnId])` so the categorizer gets another shot.
- The three SQL fragments are drizzle `sql` template exports built against the schema objects so the join composes into existing query builders. Exact drizzle form:

```ts
import { sql } from 'drizzle-orm';
import { transactions, transactionSplits } from '@/db/schema';
export const EFFECTIVE_CATEGORY = sql<number | null>`coalesce(${transactionSplits.categoryId}, ${transactions.categoryId})`;
export const EFFECTIVE_AMOUNT = sql<number>`coalesce(${transactionSplits.amountCents}, ${transactions.amountCents})`;
// consumers write: .leftJoin(transactionSplits, eq(transactionSplits.txnId, transactions.id))
```

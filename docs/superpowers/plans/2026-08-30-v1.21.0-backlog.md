# v1.21.0 backlog

Items raised by the owner after v1.20.0 shipped, logged one at a time as they come in.
Each entry records the ask, the decision made about it, and why — so the reasoning survives
into whoever implements it.

Nothing here is started. Items are in the order they were raised, not priority order.

---

## 1. Budgets: scope pills instead of stacked sections

**Ask:** the Budgets page is very long, because it renders a household section and then one
personal section per person. Put pills at the top — Household plus each person — and show only
the selected one.

**Decision: do it, reusing the dashboard's existing person-scope nav and its `?person=` param.**
Not a new control. The dashboard already has exactly this nav ("Whose money to show"), and a
second implementation of the same idea is the drift v1.20.0 spent a release removing.

**One deliberate difference from the dashboard, and it matters.** On the dashboard the pills
filter *whose money* — one dataset, narrowed. On Budgets they select *which set of budgets*:
household and personal budgets are separate records with their own limits, not one set viewed
through a filter. A naive filter would therefore throw away the overview — you would no longer be
able to see how the household is doing without clicking back.

**So the pills control the category grid, not the summary.** The metric cards at the top keep
showing household and per-person totals at every setting; only the grid below follows the pill.
Overview preserved, length solved.

Falls out of that:

- **A self-scoped viewer gets no pills at all** — ruling R2 already means they never see the
  household scope, and `page.tsx` deliberately does not even run the household query for them.
  The pills must not be the thing that leaks its existence.
- **Default to Household**, since that is the shared money and the common case.
- **No "All" pill.** It would rebuild the exact page being complained about, and habit would send
  people straight to it. Trivial to add later if it is actually missed.
- Pills and the month nav share the header's action column, the way the dashboard stacks its own
  rows — `PageHeader`'s slot is a row now, so a caller wanting stacked rows wraps its own column.

**Watch out for:** `suggestionsFor` / `sinkingFundsFor` are called once per section on purpose
(see the docblock at `budgets/page.tsx:93`) — their maps are keyed by category id with no scope of
their own, so rows must never be concatenated across scopes. Whatever selects the visible scope
must keep that per-scope call shape intact rather than merging first and filtering after.

## 2. Budgets: a parent's own spend has no row, so the breakdown does not add up

**Ask (owner, with a screenshot):** the Health card reads $628.55 while its three sub-categories
show $183.55, $0.00 and $0.00. "Health parent is a parent item but then shows as a child to that
i can allocate transactions too. anything i allocate to parent name doesnt show in this."

**Confirmed — the owner's diagnosis is correct.** `foldRollup` (src/lib/budgets.ts:222) seeds the
rollup with the parent's OWN direct spend and then adds each child:

    return childIds.reduce((sum, id) => sum + (spendByCategory.get(id) ?? 0),
                           spendByCategory.get(categoryId) ?? 0);

That seed is right — money spent on Health is Health spending. But `BudgetCategoryCard` renders
only `row.children`, so the seed has no row anywhere and roughly $445 of real spend is invisible
while still counted in the headline. The page looks like it cannot add up, which costs trust in
every other figure on it.

**Ruled out:** archived children. v1.12.1 (item S / MON-1) already fixed that exact shape — an
archived child still carrying spend surfaces as a read-only row specifically so its spend cannot
count against a parent invisibly. This is the same class of defect in a place that fix did not
reach.

**Decision: render the parent's own spend as a row inside its own breakdown**, labelled
*Not in a sub-category*, only when non-zero.

- Nearly free to implement: `categoryTransactions` already filters `EFFECTIVE_CATEGORY =
  categoryId` exactly, so "View transactions" on that row returns precisely the direct rows with
  no query change.
- The card's eyebrow currently reads "N categories · M over". It must read "N sub-categories" —
  the direct bucket is not one of them.
- The direct bucket has no limit of its own, so it must never count toward the "· M over" tally.

**Rejected: forbidding assignment to a parent category.** Structurally the purer model, but it
needs a migration for every transaction already sitting on a parent and it removes a legitimately
useful move (sometimes a pharmacy run is just Health). The display is what is lying here, not the
data.

**Owner confirmed (follow-up):** assigning to a parent stays, and it must show up in reports.

**Reports: checked, not assumed.** Rolled-up reports are already CORRECT. `categoryBreakdown`
(src/lib/reports.ts:103, and the same rule again at :309) folds with
`const target = category?.parentId ?? categoryId` — a category with no parent maps to itself, so
direct-to-parent spend lands in the parent's bucket exactly as its children do, and the total
agrees with the Budgets headline. Nothing to fix there.

**But un-rolled reports carry the same lie in different clothes.** With rollup off, the breakdown
emits a row named literally "Health" beside "Pharmacy" and "Dental". That row is ONLY the direct
spend, while its name reads as the parent — so on Budgets the money is invisible and on Reports it
is mislabelled. Same defect, same money.

**One vocabulary fixes both.** Whatever the bucket is called in the Budgets breakdown
(*Not in a sub-category*) is what the un-rolled Reports list calls it too, for a parent category
that also carries direct spend. A leaf top-level category with no children keeps its plain name —
there is nothing to disambiguate it from.

**Priority: ahead of item 1.** A visibly wrong total is worse than a long page.

## 3. Transactions: a parent category chip hides every child

**Ask (owner, with a screenshot of the chip row):** "filter on page transactions only filter where
i directly assign parent and ignore all child".

**Confirmed.** src/lib/transactions.ts:144 filters on an exact id:

    else if (typeof filter.categoryId === 'number')
      clauses.push(eq(transactions.categoryId, filter.categoryId));

The chips are top-level categories, so clicking Health lists only rows assigned directly to
Health while the Health budget card counts Pharmacy, Dental and Fitness too. Two pages, two
meanings for one word. This is the same defect family as item 2 — a parent means "itself plus its
children" everywhere except the places a person actually looks.

**Decision: a parent chip means the parent AND its descendants**, matching `foldRollup`
(budgets) and `categoryBreakdown`'s `parentId ?? categoryId` (reports).

**It needs a second, explicit mode**, because item 2 introduces a link that wants the opposite:
the *Not in a sub-category* row's "View transactions" must show ONLY the directly-assigned rows.

- `category=<id>` — the category and its children. What a chip does.
- `category=<id>&exact=1` — that category alone. What item 2's drill-down does.

One filter, two stated meanings, neither inferred. The category tree is two levels deep today;
implement descendants as "this id plus its children" and say so, rather than writing a general
recursive walk for a depth that does not exist.

**Second defect found while checking this, not yet reported by the owner.** The same filter reads
`transactions.categoryId`, while every TOTAL in the app reads `EFFECTIVE_CATEGORY` (split-aware —
see src/lib/splits.ts, and `categoryTransactions`'s own docblock). So a transaction split with $50
to Health counts toward the Health budget but does NOT appear when Transactions is filtered by
Health: the list contradicts the number that linked to it. Fix both together — they are the same
question ("which rows are in this category?") answered two ways in one codebase.

**Watch out for:** the chip counts and the "Needs review (N)" count must be computed through
whatever rule the filter ends up using, or the count and the list disagree again in a new place.

## 4. Dashboard: "Spent this month" and "Net this month" count different transactions

**Ask (owner, with a screenshot):** "dashboard has misleading numbers. i think its taking into
account transfers?"

**It is NOT transfers** — those are excluded from both sides (src/lib/reports.ts:44, and the
budgets path excludes them too). The owner's instinct that something is double-counted was right;
the cause is different.

**On the screenshot:** Money in $13,775.09 − Spent $13,468.48 = +$306.61, but Net reads
−$5,693.39. The gap is exactly $6,000.00, which is uncategorized outflow.

**The two tiles read different sets:**

- **Net / Saved this month** come from `cashflowTrend`, whose rule is stated at reports.ts:151:
  "Income counts ONLY is_income categories; everything else (including uncategorized rows) is
  spend, netted."
- **Spent this month** is `totals.totalSpentCents` from `budgetProgress`, which sums spend PER
  CATEGORY. A transaction with no category produces no category row, so it is absent from that
  sum entirely.

Each tile is internally correct. Side by side they contradict each other, with nothing on screen
explaining why, which is the whole complaint.

**Decision: Net is the honest one.** Money spent is spent whether or not it has been filed yet.
"Spent this month" is really "spent, among things I have categorized", and it does not say so.

**Fix: the Spent tile counts everything**, so `Money in − Spent = Net` reconciles on the face of
the card. The budget-relative figure keeps its existing home in the hint and the progress bar
("X of Y budgeted"), which is where a budget comparison belongs. When uncategorized spend exists,
the tile says so — "$6,000.00 not categorized yet" — linking to the review queue. That turns the
contradiction into the app's best nudge to go and categorize.

**Check as part of this item, do not assume:** the same screenshot's Cash runway reads "no
spending history yet to average" while the page shows $13k of spend. That smells like the same
categorized-only rule seen from another angle. Verify before deciding whether it is one fix or
two.

**Watch out for:** MUST-13.2 — loan payments must stay visible to spend calculations. Whatever
"count everything" ends up meaning, it must not quietly start filtering rows that also repay a
loan.

## 5. Dashboard: the 12-month cashflow chart is unreadable with little history

**Ask (owner, with a screenshot):** "it affects this chart too i think".

**It does NOT** — worth stating plainly so nobody "fixes" it twice. `SavingsChart` is fed from
`cashflowTrend`, the same source as the Net tile, so it already counts uncategorized spend under
the honest rule. When item 4 lands, the Spent tile will come into agreement with THIS chart, not
the other way around.

The chart does have its own defects, all visible in the screenshot:

1. **Months with no history are plotted as zeros.** `cashflowTrend` seeds every key in the
   requested range with 0 (`for (const m of months) result.set(m, 0)` shape), so a month before
   the first transaction renders as "earned 0, spent 0, saved 0" — indistinguishable from a month
   where the household genuinely broke even. Ten such months squeeze all the real data into the
   last few percent of the width. A month with no data should be ABSENT, and the card should stop
   claiming "12-month" when only one month of history exists.
2. **Five series, three of them indistinguishable.** Cumulative saved, Net and Target all render
   as near-identical purple lines; the legend cannot be matched to the plot.
3. **A Target line is drawn when no target is set.** The Saved tile beside it reads "No savings
   target set for this month yet" while Target still appears in the legend at a flat ~19500.

Plus a dual y-axis (left 19500…−6500, right 0…−6000) with nothing indicating which series reads
against which scale.

**Direction (not yet decided in detail): split the card.** Bars for income and spend against one
axis, cumulative saved as its own smaller chart, target drawn only when one exists. That removes
the dual axis and the colour collision together.

**When building this, load the `dataviz` skill first** — series colour, dual axes and empty-state
handling are exactly what it covers, and this card has already been through one pass that
eyeballed it.

## 6. Loans: a loan's balance could only be repaired by deleting and recreating it

**Ask (owner, with a screenshot of a loan detail page):** the balance was wrong and they had to
delete the loan and create a new one to fix it. Their guess, in their words: "if i add + value to
the loan first and then add -native value it shows balance of -ve as it was added later?" — i.e.
that the sign follows the ORDER payments were linked rather than each transaction's own direction.

**Shape of the case** (amounts kept, descriptions and names deliberately not recorded — this is a
public repo): a "lent out" loan with three hand-linked payments — an outbound transfer of
$6,000.00, an inbound transfer of $6,000.00 the next day, and a small card purchase of $11.29. The
page now reads "Balance still owed to you $11.29", which is arithmetically CORRECT for that set
(lent out, repaid, plus a further charge on the borrower's behalf). The current state is right
because the loan was recreated; the fault is somewhere on the path that preceded it.

**Two candidate mechanisms, not yet resolved — a read-only trace is running:**

1. The owner's hypothesis: the applied sign comes from insertion order rather than from the
   transaction's own direction. Note both $6,000 rows display "Applied $6,000.00" as a positive
   figure, so the direction is recovered somewhere else.
2. More likely on the evidence: the balance is a STORED figure with a snapshot date. The page says
   "You set this on 2026-08-31" and warns "Removing an old payment can push the balance above your
   latest statement figure." If payments dated before the last manual balance update are skipped
   — or applied when they should not be — then WHEN each payment was linked changes which ones
   count, which reproduces the symptom exactly without order-of-insertion being the cause.

They need different fixes, so the trace resolves which before anything is written.

**Independent of the mechanism, one thing is already established:** needing to delete and recreate
a loan means some state reached a shape the UI had no way to repair. Whatever the arithmetic fix
turns out to be, there must be a route back — either an explicit recompute-from-payments action,
or making the balance DERIVED from the payment set so there is no stored figure left to corrupt.
The second is the stronger fix and should be weighed seriously: a derived balance cannot drift.

**Related invariants to keep intact:** ruling P4 (one helper owns the sign flip — `loanSignedDelta`
/ `isLoanRepayment`, and `src/lib/loans.ts` must never spell 'lent' itself), and MUST-13.16
(exactly one delete path, which must call `reverseLoanLinksForTransactions` BEFORE deleting —
a cascade removes link rows but cannot restore a balance).

## 7. Dashboard: Net worth states a confident figure while excluding accounts

**Ask (owner):** "where is the net worth coming from? this makes no sense" — screenshot shows
"+$20,168.62" with the hint "4 accounts have no balance yet".

**Where it comes from** (src/lib/networth.ts:298-346): the latest balance snapshot per active
account resolved as of the month end — positive balances summed as assets, negative as debts —
minus the loans owed, from `debtOverTime`. An account with NO snapshot is skipped entirely
(`accountsMissing += 1; continue;`) rather than counted as zero. So the figure is the net worth of
whichever accounts happen to have a balance.

**Three defects, increasing in seriousness:**

1. It reads as complete. A large positive figure in the positive tone, with the caveat in small
   text below that says what is missing but never says the number EXCLUDES it.
2. With four accounts missing, neither the magnitude nor the SIGN is trustworthy. If those
   accounts are credit cards, real net worth may be negative. Rendering it green and positive is
   a claim the data does not support.
3. The same dashboard already handles this correctly one tile over: Cash runway shows "—" and
   says "1 account missing a balance — this figure is incomplete." Two tiles, same gap, opposite
   treatments. Cash runway is the right one.

**Decision: when `accountsMissing > 0`, the tile must stop asserting.** Keep the figure (it is
genuinely useful) but mark it partial, drop the positive/negative tone since the sign is not
established, and say plainly that N accounts are excluded — with a link to set them, the way the
Reports net-worth card already offers "Update ... in Settings and Accounts". `netWorthHint` is
already the single source of that wording (see its docblock, Defect 2 of the 2026-08-23 review),
so the tone/marking decision belongs beside it rather than in the tile.

**Separate defect found while tracing, NOT reported by the owner:** `debtOverTime` returns both
`owedCents` and `lentCents`, but `netWorthOverTime` only adds `debtByMonth` (the owed side) to
debts. Money LENT OUT is never counted as an asset. So a loan reduces net worth when you owe it
and does nothing when you are owed it. Determine whether that asymmetry was deliberate (an
argument exists — a debt owed to you may never be repaid) and, if so, say so in the code; if not,
count it. Either way it should not be silent.

## 8. Top merchants: lent-out money counted as spend, and store numbers split one vendor into many

**Ask (owner, with a screenshot):** "transfers show here which doesn't make sense. then walmart
each store is separate desc so it never shows the right value... is there a way of adding logic
where app decides vendor based on desc?"

### 8a. The "transfer" is not a transfer — it is a loan disbursement counted as spend

`topMerchants` already excludes transfers (src/lib/reports.ts:403 applies `rangeClauses`, which
carries `eq(transactions.isTransfer, false)`). The $6,000 outbound e-transfer appears because it is
NOT flagged as a transfer: it is the disbursement of a loan the household made.

**This is the same transaction as item 4's unexplained $6,000.** One row, surfacing wrongly in
three places: the Net/Spent discrepancy, this list, and (by its absence) the net-worth asymmetry
in item 7. Fixing the rule fixes all three.

**Proposed rule: repaying a loan you OWE is spending; lending money OUT is not.** A car payment
belongs in Transport and MUST-13.2 exists precisely to keep it there — but that invariant speaks
to repayments of debts owed, not to money handed out, which converts cash into a receivable rather
than consuming it. The two are opposite directions and only one is spend.

Do this together with item 7's `lentCents` asymmetry: today, lending $6,000 makes the books
$6,000 poorer twice — once as phantom spend, once as an asset never counted.

### 8b. Vendor standardisation already exists and has two specific gaps

`normalizeMerchant` (src/lib/categorize/normalize.ts:115) already strips channel prefixes, STORE
and UNIT markers, `#1234`, digit runs of 5+, reference tokens, and a trailing `CITY PROVINCE`
tail. A big-box store's rows still split because:

1. **Short store numbers survive.** The digit-run rule requires 5+ digits; a 3-4 digit store code
   not preceded by `#` or `STORE` is kept as if it were part of the name.
2. **A bare trailing city survives.** The location rule only fires when the LAST token is a
   province code; `... CITYNAME` with no province is not matched.

**Decision: widen those two rules, keep the normaliser DETERMINISTIC.** No fuzzy matching, no
learned clustering. A wrong automatic merge silently combines two real merchants into one total
and the person has no way to notice; an explainable rule can be read, tested and corrected.

**Add the missing half: make the grouping visible and correctable.** Merchant rules (pattern +
display name) already exist as the override mechanism. What is missing is seeing WHICH raw
descriptions were folded into a displayed vendor, and being able to split or re-map them in one
action from where the total is shown — rather than discovering a bad merge inside a number.

**Care needed:** changing normalisation retroactively changes historical grouping. Establish
whether `normalized_merchant` is stored at import time (it is a column on transactions) and, if
so, what re-normalising existing rows would do to merchant rules and to the categorizer's learned
associations before touching it.

### Item 6 — RESOLVED by a read-only trace. Mechanism confirmed.

**The owner's hypothesis is PARTLY correct: order matters, but not through the sign.**

**The sign is sound.** `loanSignedDelta`/`isLoanRepayment` (src/lib/warranty/constants.ts:293) is
recomputed fresh from the loan's direction and the transaction's immutable amount on every path —
`link` (loans.ts:302), `unassignTransactionFromLoan` (:899), `reverseLoanLinksForTransactions`
(:953), `itemLedger` (:1117). Ruling P4 holds. `loan_payments.applied_cents` is stored unsigned by
design (docblock at loans.ts:262), which is why both $6,000 rows read "Applied $6,000.00".

**Hypothesis 2 (the snapshot date) is WRONG.** `balance_updated_at` never appears in any write or
apply path as a filter — loans.ts:325 documents it explicitly: "MUST-11.8: balance_updated_at is
NOT touched. It is the human anchor." It is display text plus chart reconstruction, nothing more.

**The real defect: `current_balance_cents` is a STORED accumulator, and `link()` clamps a repayment
against its value AT THE MOMENT OF THAT CALL** (loans.ts:307,
`Math.max(0, Math.min(magnitude, balanceCents))`). Growth applies unclamped and in full. So a
repayment linked BEFORE the growth that justifies it is silently truncated, and the excess is
discarded permanently — never stored, never reported, no warning.

Reproducible sequence for a 'lent' loan, matching the reported case exactly:

1. link -$11.29 (growth) -> balance $11.29
2. link +$6,000.00 (repayment) -> applied = min(6000, 11.29) = $11.29, balance $0.
   **$5,988.71 is lost.**
3. link -$6,000.00 (growth) -> balance $6,000.00

Displayed: $6,000.00. Correct: $11.29. Never negative (the clamp floor and the DB CHECK at
schema.ts:613 both forbid that) — just permanently too high and silent.

**This is pinned as intended behaviour by an existing passing test**
(tests/lib/loans/manual-assign.test.ts:115, "a repayment larger than the outstanding balance clamps
at zero, never below"). It was a deliberate decision with a hole in it, so fixing it means changing
that test with an argument, not deleting it.

**Reachable only via manual assign.** The rule matcher and backfill both skip `amountCents >= 0`
(loans.ts:556, :638), and for a 'lent' loan a repayment is always the positive case — so only a
hand-linked transaction can trigger it. `createLoanFromTransaction`'s LOAN_LENT_FIRST_ENTRY_ERROR
guard protects only the very first link, not any later assign.

**Reversal is symmetric and NOT at fault.** Unlink and `reverseLoanLinksForTransactions` restore
exactly the `applied_cents` recorded, correctly undoing whatever `link()` actually did. The
asymmetry is inside `link()` alone: `applied_cents` can differ from the transaction's true
magnitude, and that difference is the permanent loss.

**A cheaper repair than delete-and-recreate exists but is undiscoverable:** unlink the truncated
repayment and re-link it after the growth is present. The restore adds back the clamped figure,
the re-link then sees a sufficient balance and applies in full. Nothing in the UI suggests this.

**Delete-and-recreate works because** `loan_payments.item_id` cascades on delete (schema.ts:961)
and `current_balance_cents` lives on the deleted row, so the accumulator is wiped and rebuilt.
**There is no recompute/rebuild/reconcile helper anywhere in the codebase** — confirmed by grep.

**Recommended fix: stop storing a running balance.** Derive it from the payment set on read, clamp
at zero for DISPLAY only, and record each payment's true magnitude rather than the clamped one.
Order then cannot matter, because there is no accumulator left to corrupt. Second-best, if the
stored figure must stay for query cost: record the true magnitude, surface an explicit warning when
a repayment exceeds the outstanding balance instead of silently absorbing it, and add a
recompute-from-payments action so a corrupted loan can be repaired without deletion.


### Item 8b — REVISED after discussion with the owner

**Owner's proposal:** expose vendor normalisation in Settings the way category rules already are,
so a rule can say "contains WALMART" or "contains SHELL" rather than matching an exact string.

**That capability already exists and is shipped.** `merchant_rules` carries
`match_type: 'exact' | 'contains'` and `rule_kind: 'rename'` with a `rename_to` target
(src/db/schema.ts:292). `matchRule` (src/lib/categorize/rules.ts:38-61) implements `contains` with
LONGEST-PATTERN-WINS precedence, so a specific rule correctly beats a general one. The Settings
merchant-rules form already offers all three controls. Rename rules apply retroactively and are
reversible: saving one updates every matching transaction not renamed by hand, deleting one
restores the bank's wording.

**So the owner can write `contains WALMART -> Walmart` today, and it works — everywhere except the
place they are complaining about.** `topMerchants` (and the Reports merchant table) group on
`transactions.normalized_merchant`, while rename writes `display_description` + `display_source =
'rename'` (src/lib/categorize/engine.ts:793). The rule is correct; the report ignores it.

**Decision: fold the report's groups through the rename rules at READ time.** `topMerchants`
already returns buckets keyed by normalized merchant; run `matchRule(key, 'rename', rules)` across
those keys and merge buckets that resolve to the same name.

**Why fold by RULE rather than key on the stored `display_description`:** a transaction renamed BY
HAND keeps its own label and is deliberately skipped by rules. Grouping on the stored display value
would split that hand-edited row into its own bucket, away from the vendor it belongs to. Folding
by rule groups it correctly, because the row still carries its normalized value underneath.

Cheap to do: a handful of rules over a handful of group keys, no schema change, no migration, and
the buckets are disjoint so sums and `count(distinct id)` charge counts simply add.

**Still wanted alongside it:**

- **A (narrow):** widen the normaliser only where it is clearly safe — a short pure-digit token
  that is not the first token. Drop the trailing-bare-city idea unless a city list is introduced
  deliberately; guessing there merges two real merchants into one total nobody can audit.
- **A merge action on Top merchants itself**, pre-filling a `contains` rename rule from the row
  being looked at. The rules engine is finished; what is missing is reaching it from where the
  problem is noticed, rather than from Settings.
- **A match preview before saving a rule.** `contains WALMART` also catches WALMART GAS BAR.
  Longest-pattern-wins lets a second rule carve that out, but the general rule silently swallows it
  until someone notices. Show what a pattern will match, and how many rows, before it is saved.


### Item 8b — the vendor-table question, settled

**Owner's concern:** "walmart i can do shopping and groceries. so not best way to handle." Then:
how much work is a vendor table, how would it work, and how much would they have to maintain?

**First, the concern rests on a conflation worth fixing in the UI.** A RENAME rule does not touch
categories — rename and category are different `rule_kind` values on the same table. `contains
WALMART -> Walmart` changes only the displayed name; each transaction keeps its own category, so a
vendor can still span Shopping and Groceries. What WOULD be wrong for a multi-category vendor is a
CATEGORY rule, which is exactly what the "apply this category to every X" action creates. The
owner's instinct is right, aimed at the wrong rule kind. **The UI should make that distinction
obvious** — today nothing warns that "apply to every X" is a different, stickier commitment than a
rename.

**Decision: do NOT build a vendors table.**

- **One already exists in effect.** `merchant_rules` with `rule_kind='rename'` IS a pattern ->
  canonical-name mapping. A `vendors` table would add a stable id, multiple patterns per vendor as
  first-class rows, and a place to hang per-vendor metadata.
- **The metadata that justifies the build is a default category per vendor — which this household
  explicitly does not want.** Their canonical example spans two categories. The main payoff is
  absent.
- **Build cost:** two tables plus migration, CRUD screens, resolution logic, a backfill for
  existing rows, reports integration, tests. A release on its own, comparable in size to the
  savings-targets work.
- **Owner's maintenance cost is the SAME either way:** one entry per vendor whose name the bank
  splits. With `contains`, that is one rule for Walmart, one for Shell. The table would reorganise
  the work, not reduce it.

**What actually reduces maintenance — build this instead: suggested merges.** The app can detect
normalized merchants sharing a leading token that appear as separate rows in the same report, and
offer "These 5 look like one vendor. Merge as Walmart?" for confirmation. Deterministic (nothing
merges unconfirmed), and it changes the work from "notice a split, go to Settings, write a rule"
to one click where the problem is visible. Realistically the household handles its top 20-30
vendors once, then new ones as they appear.

**Final shape for vendor standardisation:**
1. Fold report groups through rename rules at read time (the core fix).
2. Widen the normaliser only where clearly safe (short non-leading digit tokens).
3. Merge action on Top merchants, pre-filling a `contains` rename rule.
4. Match preview before saving any rule — pattern, and how many rows it will catch.
5. Suggested merges from near-duplicate normalized merchants.
6. Make the rename-vs-category distinction visible where both are offered.

## 9. Merchant rules: a lowercase pattern silently never matches

**Found while walking the owner through creating their first rename rule.**

`normalized_merchant` is always uppercase (`normalizeMerchant` starts with
`raw.normalize('NFC').toUpperCase()`, src/lib/categorize/normalize.ts:116). `matchRule` compares
with `normalizedMerchant.includes(rule.pattern)` and `rule.pattern === normalizedMerchant` —
no case folding on either side (src/lib/categorize/rules.ts:46-51). The save path only trims:
`pattern: z.string().trim().min(1).max(200)` (settings/managers/actions.ts:128).

**So a rule saved as `walmart` is accepted, stored, listed in the table of 109 rules, and matches
nothing — forever, with no error and no hit count to reveal it.** The rule looks real in every UI
surface; it is simply dead.

**Owner's call: make it case-insensitive.** From the person's side both options are the same —
type any case, it works. They differ only in what is stored.

**Decision: uppercase the pattern on SAVE**, rather than fold case at match time.

`normalized_merchant` is already canonically uppercase (normalize.ts:116). Making patterns
canonical too keeps the stored data consistent, leaves the comparison a plain string match, and
lets `merchant_rules_pattern_uq` keep doing its job. Folding case only at match time would let
`walmart` and `WALMART` exist as two distinct rows that behave identically — two indistinguishable
entries in the rules list, with matchRule's longest-then-lowest-id tiebreak silently picking one.

**The migration is the hard part, and it must not be a one-line UPDATE.** This household already
has 109 rules. Uppercasing them can collide: if `walmart` and `WALMART` both exist they become one
row and the unique index rejects the write. The migration has to MERGE — keep one row, carry the
higher `hit_count` and the earlier `created_at`, drop the duplicate, and record what it merged so
the result is auditable. Doing this at 109 rules is cheaper than at 300.

**Either way, the form should not accept a pattern that matches zero existing transactions without
saying so.** That is the same "match preview" already wanted in item 8b: show what a pattern
catches, and how many rows, before saving. A rule that matches nothing today may be intentional
(anticipating a future merchant), so this is a warning, never a block.

**Also worth checking:** whether any of the 109 existing rules are dead for this reason. A
one-off report of rules with `hit_count = 0` and no current match would show it.

**Agreed.** 109 rules today, rendered as a flat table inside a card on a shared Settings page.

**Reuse the Transactions page's machinery rather than growing a second one.** That page already

2. Search across pattern and rename target.
3. Filter chips by `rule_kind` — category / rename / transfer / not_transfer. Four kinds doing four

**Relates to:** item 9 (dead rules to find), item 8b (the merge action writes rules, so it will
accelerate the growth this page has to absorb).

## 11. Rules: disable instead of delete, and re-run them over existing data

**Ask (owner):** "lets add archive if not delete. also can we add a logic to that after adding or
archiving a rule i can re-run the categorization on older data if i want? or the rename rule if i
want? currently i added rename rules it will only fix future data. no?"

### The premise is half wrong, and the wrong half probably explains their experience

**Rename rules ARE already retroactive.** settings/managers/actions.ts:145 — "Rename rules go
through the engine so the change is applied retroactively" — calls `upsertRenameRule` and reports
"Rename rule saved and applied to N transactions." The engine's reapply pass
(src/lib/categorize/engine.ts:765-799) updates every matching row that was not renamed by hand,
and clears rows whose rule no longer resolves.

**So if the owner's rename rules only appeared to affect future data, the likely cause is item 9:**
a lowercase pattern matches nothing, so the message would have read "applied to 0 transactions" and
nothing would ever change. Worth checking the case of the rules they already added.

**Category, transfer and not_transfer rules are NOT retroactive.** `upsertRuleFromCorrection` just
writes the rule; there is no backfill. The owner's request is real, and specific to those three
kinds.

**The asymmetry is itself a defect:** one rule kind rewrites history, three do not, and the form
says nothing about which behaviour you are getting.

### Re-run

Build it two ways:

- **Per-rule "Apply now"** on the rule's own row — scoped, understandable, safe.
- **Global "Re-run rules"** for after a batch of edits.

**Invariant: never overwrite a human decision.** A re-run may touch rows that are uncategorized,
machine-guessed, or previously set by a rule; it must never touch one categorized by hand. The
rename engine already implements exactly this rule (hand-renamed rows are skipped via
`display_source`), so the pattern exists to copy rather than invent — find the equivalent source
marker on the category side and use it.

**Report a count before and after.** "This will change 214 transactions" is the difference between
a useful button and a frightening one.

### Disable, not archive

Agreed on not deleting, with a wording correction: for a rule, **disable** is the accurate verb —
a switch that can be flipped back, not history being filed. One nullable column; matching skips
disabled rules.

**Disabling a rename rule must revert its rows** exactly as deleting does, or display names are
left behind with no rule to explain them. The engine already does this: when no rule resolves for
a row it previously set, it clears `display_description`/`display_source`.

**Keep delete** for genuine mistakes — 109 disabled typos is no better than 109 live ones.

**Belongs with item 10** — the rules page is where disable, re-run and bulk actions all surface.

## 12. `hit_count` does not mean "this rule works"

**Found while the owner was verifying a freshly created rename rule that showed 0 hits.**

`bumpRuleUsage` (src/lib/categorize/rules.ts:197) has exactly one caller: the categorize run's
tail (src/lib/categorize/engine.ts:245), which fires during import-time categorization. The
retroactive rename application path (`upsertRenameRule` -> the reapply pass at engine.ts:765) never
increments it, and rename resolution sits outside the loop that collects `ruleHits`.

**Consequences:**

1. A rename rule shows `hit_count = 0` permanently, however well it is working. The rules table
   displays that column, so the UI actively suggests a working rule is dead.
2. Item 10's proposed "sort by hit count to find dead rules" is invalid for rename rules — see the
   correction recorded there.
3. The owner cannot currently distinguish "this rule matches nothing" (item 9's lowercase trap)
   from "this rule works but never bumps a counter". Those need to look different.

**Fix direction:** either bump usage from every path that applies a rule (including the retroactive
rename pass, counting rows updated), or stop displaying a counter that only means something for one
rule kind and show a per-kind "currently affects N transactions" figure computed on demand. The
second is more honest — a hit count is a history of import events, while what a person actually
wants to know is what the rule is doing to their data right now.

## 13. Loan movements: classify by what the money did, and label the row

**Ask (owner):** confirms the $6,000 appears in Reports too (Category breakdown's Uncategorized
bar, Top merchants, the cash-flow chart). Proposes: a budget category "LOAN" as a parent; assigning
a transaction to a loan auto-categorizes it there and rewrites the description to "Loan to
<person>", with repayments landing in a matching child. Their own worry: "what i don't know is if
this will mess up budgeting categories". Minimum acceptable outcome, in their words: change the
description so they can see what the $6,000 is.

**Yes, item 8a clears all of it.** The $6,000 is ONE transaction surfacing as: the Uncategorized bar
in Category breakdown, the top row of Top merchants, the spend column of the cash-flow chart, and
the Spent/Net contradiction in item 4. One classification change removes it from every one.

**Reject the budget-category mechanism — the owner's own worry is the reason.** A budget category
means "money consumed". Putting lending in one keeps $6,000 counted as spend and merely relabels it
from Uncategorized to Loans; "Spent this month" stays wrong. There is also no third state to reach
for: a category is income or spend (`is_income`), with no "neither" flag, and adding one touches
every query that filters on it.

**Classify by what the money did instead:**

| Movement | Treatment |
|---|---|
| Lending money out (money out, 'lent' loan) | NOT spend — cash became a receivable |
| Being repaid (money in, 'lent' loan) | NOT income — receivable became cash |
| Borrowing (money in, 'owed' loan) | NOT income |
| Repaying a loan you owe (money out, 'owed' loan) | **Spend**, deliberately — MUST-13.2 |

The last row only looks inconsistent: a car payment is a real monthly expense a household budgets
for, which is what MUST-13.2 protects. Money handed to a friend is not consumption — it returns.

**Adopt the description half of the proposal in full — it is the good part.** On assigning a
transaction to a loan, set `display_description` automatically ("Loan to <item>" / "Repayment from
<item>") with its OWN `display_source` value (e.g. 'loan'), distinct from 'rename' and 'manual'.
The transactions row already renders a provenance badge for rule-renamed rows, so this gets a
`loan` badge beside it for free. Unlinking reverts the description, exactly as deleting a rename
rule does — the engine's "clear what this source set" pass is the pattern to copy.

Net effect: no new category, no budgeting damage, the money leaves the spend totals, and the row
reads as what it is everywhere it appears.

**Available to the owner TODAY as a workaround:** the assign-to-loan editor already carries an
"also mark as transfer" checkbox (shipped v1.20.0). Ticking it removes the row from every report,
since transfers are excluded everywhere. The fix above makes that automatic for principal movements
rather than something to remember.

## 16. Merchant rules: `contains` has no word-boundary option, so a short pattern is unsafe

**Found 2026-08-31 while building the Canadian merchant rules pack (`packs/canadian-merchants.json`,
see `docs/CANADIAN-MERCHANT-RULES-PACK.md`).**

`matchRule` (src/lib/categorize/rules.ts:49-73) implements `contains` as a plain
`normalizedMerchant.includes(rule.pattern)` — no word-boundary check on either side. That is fine
for a distinctive multi-word brand (`TIM HORTONS`, `CANADIAN TIRE`), but a short pattern matches
anywhere inside a longer, unrelated word:

- `IGA` (Groceries) matched inside `MICHIGAN` (`normalizeMerchant('MICHIGAN AVE SHOP #55
  WINDSOR ON')` → `'MICHIGAN AVE SHOP'`, which `'MICHIGAN AVE SHOP'.includes('IGA')` is `true`).
- `MAXI` (Groceries) matched inside `MAXIMUM`.
- `ESSO` (Gas) matched inside `PROFESSOR` and `ACCESSORY`/`ACCESSORIES`.
- `RONA` (a rename rule, Hardware) matched inside `CORONA`.
- A bare possessive-brand stem (`LOWE`, before it was fixed to `LOWE'S`) matched inside `FLOWERS`
  (`F-L-O-W-E-R-S` contains `L-O-W-E`).

**Why `exact` is only a workaround, not a fix.** The Canadian pack ships `IGA`, `MAXI`, `ESSO`,
`RONA`, `KFC`, `A&W`, `TTC`, `STM`, `F45`, `YMCA`, `XBOX`, and `FIDO` as `exact` rather than
`contains`, because `exact` requires the WHOLE normalized merchant to equal the pattern, which
sidesteps the substring collision entirely. That works only because `normalizeMerchant()` already
strips store numbers and the trailing `CITY PROVINCE`, so a real transaction for one of these
merchants often normalizes to exactly the bare pattern. It stops working the moment a real
descriptor carries anything else — a suffix (`F45 TRAINING <location>`), a second word
(`XBOX GAME PASS`), a franchise qualifier — at which point `exact` simply misses it, and the only
recourse today is adding a second, longer `contains` rule for that specific suffix (which the pack
does for `FIDO MOBILE`, `F45 TRAINING`, `XBOX GAME PASS`, and `MAXI & CIE`). That is a per-pattern
patch, not a general answer, and it does not help a pattern that is short AND needs to stay broad —
`FORTIS` and `ATCO` (Utilities) are shipped as `contains` anyway, accepting a real (documented)
risk of catching a diversified holding company's non-utility business, because there is no way to
keep them broad enough to catch every subsidiary spelling without either that risk or an unbounded
list of subsidiary names.

**What a `word` match type would do differently.** Match a pattern only when it is bounded by a
non-alphanumeric character (or string start/end) in the normalized merchant on BOTH sides — the
same `[^${ALNUM}]` class `normalize.ts` already defines for tokenizing. `IGA` as `word` would match
`IGA #4021` (bounded by a space) but not `MICHIGAN` (bounded by letters on both sides), so it could
stay `contains`-broad (matching a real suffix like `IGA EXTRA`) without the collision `exact`
was adopted specifically to avoid. It would also make `FORTIS`/`ATCO` safer without dropping their
breadth, since a subsidiary spelling (`FORTISBC`) has no boundary before its own suffix but a
transaction merchant field boundary (space, `#`, string edge) still exists around the merchant name
as a whole in the cases that actually matter.

**What would need to change:**

- `matchRule` (src/lib/categorize/rules.ts) needs a third branch alongside `exact` and `contains`,
  reusing `normalize.ts`'s `NON_ALNUM_RUN`-style boundary class rather than inventing a second
  definition of "boundary" that could drift from the tokenizer's own.
- `MatchType` (currently `'exact' | 'contains'`, src/lib/categorize/rules.ts:6) and every zod enum
  that validates it — the rule-save form (`saveRuleAction`, settings/merchant-rules/actions.ts) and
  `packRuleSchema`'s `match_type: z.enum(['exact', 'contains'])` (src/lib/packs.ts) — need the new
  value added, including on the IMPORT side so a pack from a newer install carrying `'word'` fails
  gracefully rather than silently mis-parsing on an older one (the same PACK_VERSION gate other
  forward-compat breaks already use, or an explicit case in `isImportableRuleKind`-style handling).
- A migration is needed only if existing `contains` rows should be OFFERED a switch to `word` (e.g.
  a one-time report of `contains` rules under some length threshold, similar in spirit to item 9's
  "report rules with hit_count = 0") — adding the match type itself needs no migration, since it is
  a new enum value on an existing column, not a data rewrite.
- The rules page's match-type filter/select (`src/app/(app)/settings/merchant-rules/`) needs the
  third option, and its explanatory copy needs to say what `word` means in plain language (“matches
  a whole word, not letters inside a longer word”) — this is exactly the kind of distinction a
  household member setting up a rule cannot be expected to infer from `exact` vs `contains` alone.

Not implemented. Recorded so the next person who reaches for `exact` as a workaround for a short
pattern knows it is a workaround, and knows what the real fix looks like.

## 17. An imported pack cannot be un-imported

**Ask (owner, after v1.22.0 shipped the Canadian pack):** "can i un import the pack later?"

**Today: no.** `merchant_rules` carries no provenance — no source, no pack name, no imported-at.
Once `importRulesPack` writes them, 190 pack rules are indistinguishable from the 109 the household
typed themselves. There is nothing to undo BY.

The workarounds that exist are real but blunt: take a database backup before importing (Settings →
Backups) and restore it, which reverts everything else too; or export your own rules first so you
hold a copy; or find and bulk-delete the imported ones by hand on the rules page, which is
tedious at 190 rows and error-prone where a pack pattern happens to match one you already had.

**Proposed fix, small and well-shaped:**

1. **Stamp provenance on import.** A pack identifier plus an imported-at timestamp on each row
   `importRulesPack` writes. Rules written any other way (the form, `confirmCategory`,
   `applyCategoryToMatching`) leave it null, so "typed by a person" stays distinguishable from
   "arrived in a batch".
2. **"Remove everything from this import"** as one action, listing what it would delete and how
   many transactions revert (rename rules put the bank's wording back — the same consequence the
   bulk-delete confirmation already states).
3. **A conflict-kept rule must NOT be stamped.** If the import kept the household's existing rule,
   that row is theirs and an un-import must not delete it. This is the subtle part and the reason
   the feature needs the stamp rather than pattern-matching against the pack file.
4. **Bonus this unlocks:** re-importing an updated pack can cleanly replace the previous one's
   rows instead of layering a second copy alongside, which is otherwise how a pack accumulates
   duplicates over versions.

**Not started; needs the owner's go-ahead.**

## 18. Editing a preset rule's PATTERN loses the link back to the pack

**Found reviewing item 17's implementation (v1.23.0), documented rather than fixed.**

A preset rule's identity is its key: `(pattern, match_type, rule_kind)`. `walkCanadianPackUpdate`
classifies a bundled pack rule by looking that key up in `merchant_rules` and checking whether the
row is still stamped:

- stamped, same outcome -> unchanged
- stamped, different outcome in the new pack -> **changed**, offered
- present but NOT stamped (the person edited it through the form, which clears provenance) ->
  **skippedEdited**, left alone. This is the guarantee that matters and it works.

**The gap:** editing the PATTERN changes the key, so the pack's original key no longer resolves to
anything. A later update therefore reports the original rule as **added** rather than as "you
changed this one", and installing it would restore a broad pattern somebody had deliberately
narrowed. Concretely: narrow `FORTIS` to a specific subsidiary, and pack v2 offers plain `FORTIS`
back.

**Severity is limited on purpose:** nothing auto-applies, an update always shows its diff first, and
the re-added rule appears in the added list where it can be declined. So this is a reporting
weakness, not a silent behaviour change — which is why it is logged rather than rushed.

**Fix when it becomes worth it:** record the pack's OWN key on the row at install time (a
`pack_key` column, or the original pattern), and keep it through an edit rather than clearing all
provenance. Then a pattern edit is still traceable to its pack entry and can be reported as
"edited (pattern changed from X)" instead of resurfacing as an addition. Note this means splitting
"which pack installed this" (kept through edits) from "does this still match what the pack says"
(the drift check) — today one nullable stamp does both jobs, which is why the pattern case falls
through.

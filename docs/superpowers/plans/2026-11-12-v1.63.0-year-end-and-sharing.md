# Year-end and sharing — Implementation Plan (v1.63.0)

**Goal:** Three things a household needs once a year or once per machine:

1. **Year-end pack.** For a chosen year: a detail CSV of every transaction (or split part) in a
   tax-relevant category, a zip holding that CSV, the existing totals CSV and the receipts linked to
   those transactions, and a Year in review card on Reports (income, spent, net, top categories,
   tax-category totals, largest purchases). Self-scoped members get the same card and downloads over
   their own rows only.
2. **Split by person.** A split part can belong to a different person than its transaction. Who spent
   it, person filters, personal budgets, reports, the tax report and the digests count each part for
   its own person. Self-scoped members see their own parts only.
3. **Restore by upload.** An admin uploads a backup archive in the browser (moving to a new NAS), and
   it goes through the existing staged restore, its checks and its warnings.

Every item lands with a test that fails on v1.62.0.

**Base:** v1.62.0 (planned in `2026-11-12-v1.62.0-faster-review.md`). Start only after its gate has
finished and it is tagged. Work on `main`, no branches or worktrees. **One migration, 0032**
(`transaction_splits` gains a person). Line numbers below are from `main` while v1.61.0 is being
built; v1.61.0 and v1.62.0 move many of them (both edit `transactions.ts`, the transactions page and
client, `predict/history.ts`, `recurring.ts`, `bills.ts`, the dashboard), so re-read before editing.

**Process (lean):** one fresh implementer per lane.
- Phase 1: Lanes A (split person, data layer) and C (restore by upload) run in parallel. Their file
  sets are disjoint.
- Phase 2: after A is committed, Lanes B (year-end pack) and D (split person, screens) run in
  parallel. Both call A's exports. C may still be running; it shares no file with B or D.

Implementers run the tests they touch, `tests/ops`, `tests/db` (Lane A), and every test file that
imports a module they change (`rg -l "<module path>['\"]" tests`). They do not commit; the
orchestrator commits each lane by file name. Then ONE review over the whole range, one fix round,
then the release gate once.

## Design decisions (every lane reads these first)

**S1. A part follows its transaction unless set.** `transaction_splits` gains `person_set`
(0/1, default 0) and `attributed_user_id` (nullable, FK users). With `person_set = 0` the part
belongs to whoever the transaction belongs to, now and after any later change of the transaction's
person. With `person_set = 1` the part belongs to `attributed_user_id`, where NULL means Household,
the meaning NULL already has on `transactions`. Every existing part is `person_set = 0`, so every
figure is unchanged until someone sets a part. Why not copy the parent's person into each part: then
Set person, attribution rules and v1.62.0's bulk undo would all have to learn to write parts, and a
bulk change would silently undo a deliberate shared split. With follow-by-default none of them
change: they write the transaction, the following parts move with it, and the set parts stay.

**S2. One fragment.** `EFFECTIVE_PERSON = case when transaction_splits.person_set = 1 then
transaction_splits.attributed_user_id else transactions.attributed_user_id end`, beside
`EFFECTIVE_CATEGORY` in `splits.ts`. An unsplit row has no joined part, so `person_set` is NULL and the
parent's person wins. Not `coalesce`: NULL is a real answer (Household).

**S3. Three reader shapes.**
- *Split-joined aggregates* (they already LEFT JOIN `transaction_splits` and sum `EFFECTIVE_AMOUNT`):
  filter and group on `EFFECTIVE_PERSON`, so every part counts for its own person and per-person lines
  stay a true partition of the household total.
- *One row per transaction* (the Transactions list, `getTransaction`): a row is in a person's scope
  when it is unsplit and theirs, or any part is theirs (`personRowClause`). Under a person scope (a
  person filter, or a self viewer) the row's amount is that person's share. A self viewer never
  receives the whole amount or the other parts.
- *Whole-charge reads* (insights, recurring charges: merchant baselines, cadences, duplicates): a
  personal read keeps a charge only when the transaction is theirs and no part is set to anyone else
  (`soleOwnerClause`). A shared charge stays in household reads. Splitting a charge's baseline per
  person is not in this release.

**S4. Who may set a part's person.** The rules that already govern Set person: a household viewer may
pick anyone attributable or Household; a self viewer may leave a part following or set it to
themselves, and may edit a split only when the transaction and every part are theirs (otherwise the
editor would replace parts they cannot see). Editing a split stays open to any member who can see the
row, as today.

**Y1. What the pack holds.** Rows: every transaction or split part dated in the year whose effective
category is in a tax-relevant category's coverage (itself and, for a parent, its children: the
`taxYearReport` rollup), `SPEND_ROW_WHERE`, scoped to the viewer (`EFFECTIVE_PERSON` for a self
viewer). Receipts: the receipt files of items linked to one of those transactions, by the item's
purchase (`warranty_items.transaction_id`) or by a bill installment it paid
(`bill_installments.paid_txn_id`). A receipt goes in only when the viewer could open it today
(`canActOnOwner(item.ownerUserId, viewer)`, the receipt route's rule); otherwise the CSV row says why
it is missing.

**Y2. The zip.** Stored entries (receipts are already-compressed JPEG/PNG/WEBP/PDF), no data
descriptors, no Zip64. Each file is read twice while streaming: once for its CRC, then for its bytes,
so headers carry real values (the most widely readable form) and memory stays at one chunk. Sizes come
from `stat` before the response starts, so `content-length` is exact. Capped at 2 GiB of receipts.

**R1. Upload in chunks.** Two platform limits make a single upload request unsafe, both verified in the
installed packages:
- Next 16 clones the body of every request the proxy runs on and keeps only the first 10 MB
  (`experimental.proxyClientMaxBodySize`, `node_modules/next/dist/server/body-streams.js`
  `getCloneableBody`), and `src/proxy.ts`'s matcher (~:127) covers `/api/*`.
- Node's HTTP server ends a request that is still uploading after 300 s (`server.requestTimeout`
  default), which Next's server does not change.

So the browser sends 8 MiB chunks (under the 10 MB clone, seconds each): start, append at an offset,
finish. A chunk can be retried, the proxy and its security headers stay as they are, and the payload
is written straight into the directory that becomes `restore-staged/`.

B3. **`src/lib/zip-stream.ts`** (built-ins only, Y2).
   - `ZipEntry = { name, date (YYYY-MM-DD), size, source: Buffer | { path } }`.
   - `zipLength(entries)` = sum of (30 + name + size) + sum of (46 + name) + 22.
   - `zipStream(entries): Readable` (`Readable.from` over an async generator): for a file, one streamed
     pass with `zlib.crc32(chunk, crc)`, then the local header (signature 0x04034b50, version 20, flags 0,
     method 0, DOS time 12:00 on `date`, CRC, sizes, name), then the bytes; then the central directory and
     the end record.
   - A file whose size differs from `size` on either pass destroys the stream with an error, so a browser
     marks the download failed rather than keeping a broken zip.
   - Names: ASCII `[A-Za-z0-9._/-]`, no leading `/`, no `..` segment, at most 200 characters, unique;
     anything else throws before a byte is written. At most 65,535 entries and under 4 GiB in total,
     else it throws (no Zip64).
   - DOS date fields are built from the date string's parts, never a `Date` in UTC.
   - Tests:
     - two entries (`a.txt` = `hello`, `b/c.bin` = 3 bytes from a temp file) read back with the
       test-side `tests/helpers/zip-read.ts`, which walks the end record and central directory, checks
       every signature and offset, and recomputes each CRC; `hello`'s CRC is 0x3610a686;
     - the stream's length equals `zipLength`;
     - when `python3` is on PATH, `python3 -m zipfile -t` accepts the file (skipped otherwise; CI's
       Ubuntu runner has it);
     - a file that grows between stat and read errors the stream;
     - a bad name and a duplicate throw before output;
     - destroying the stream part-way closes the open file (spy on the read stream's close).

  everything v1.60.0's `verifyArchive` runs (magic bytes, the tar-slip allow-list over the whole gzip
  stream, `quick_check`, required tables) plus the not-newer-than-code check. The sweep already removes

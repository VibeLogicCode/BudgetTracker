# No double counting — Implementation Plan (v1.61.0)

**Goal:** A purchase the household already has is never counted twice just because it arrived by a
second road. Today the app recognises a repeat only inside one road: bank-sync and QFX rows by the
provider id, CSV rows by the row hash (`src/lib/import/commit.ts` ~:194-203, :237), hand-typed rows by
nothing (`createManualTransaction`, `src/lib/transactions.ts` ~:1053). So quick-add then import, a CSV
then a QFX for the same account, and linking an account that has statement history to SimpleFIN all
count the same money twice. This release adds one cross-source check, used by the import preview,
every import commit and the bank sync. It also lets one imported row be deleted without the next
import or sync bringing it back, shows the overlap and asks for a start date before an account is
linked, and gives Needs review a Possible duplicates view with Keep both / Delete this one. Every
item lands with a test that fails on v1.60.1.

**Base:** v1.60.1 (the zod 4 release; v1.60.0 is `edcee72`). Start only after v1.60.1's gate has
finished. Work on `main`, no branches or worktrees. One migration, 0031.

**Process (lean):** one fresh implementer per lane. Lane A (schema and the core library) runs first
and alone, because every other lane calls what it adds; the orchestrator commits it. Then Lanes B, C
and D run in parallel. Their file sets are disjoint (listed per lane). Implementers run the tests they
touch, `tests/ops`, `tests/db` (Lane A), and every test file that imports a module they change
(`rg -l "<module path>['\"]" tests`). They do not commit; the orchestrator commits each lane by file
name. Then ONE review over the whole range, one fix round, then the release gate once.

## Design decisions (every lane reads these first)

**D1. Origin.** Each transaction records how it arrived: `transactions.origin`, one of `manual`,
`csv`, `ofx`, `simplefin`. "A different source" means a different origin. The column is needed
because QFX FITIDs and SimpleFIN ids share `external_id`, and an account unlinked from SimpleFIN and
fed QFX files again would otherwise look like one road.

**D2. Possible duplicate.** An incoming row with no exact match (hash or provider id) and no
set-aside record (D4) is a possible duplicate when the same account holds a transaction with the same
signed amount, a date within 3 days either side, and a different origin. Matching is one-to-one.
Incoming rows go in (date, file order). Each takes its nearest unclaimed candidate (tie: lower id),
and a claimed candidate cannot match a second incoming row. A row is never compared with rows of its
own origin or of its own file. So two identical same-day purchases from one source both import, as
today, and two identical rows against one hand-typed copy give one match and one import.

**D3. What happens to it.**
- *Preview:* every possible duplicate is listed (the whole file, not only the 200 preview rows), with
  a `Leave out` tick. The tick is set by default when exactly one candidate matched and clear when
  two or more did. The commit posts the choice for every listed row.
- *Commit with a posted choice:* `skip` writes a dismissed set-aside record (D4), `import` inserts the
  row.
- *Commit with no choice for that row:* the row is **held**. This covers the bank sync, a batch
  import and any client that skipped the preview. A held row is a waiting set-aside record, not a
  transaction. It shows in Needs review and counts in no figure until someone presses Keep both.
- *Why hold rather than insert-and-flag:* the preview default says "this is the same purchase", and
  holding applies that default when nobody is looking, without throwing anything away. The figures
  match what an attentive person would have chosen. An ignored hold costs a badge, and the row is
  one tap from counted. Insert-and-flag would leave Spent too high until someone looks, and hiding
  flagged rows from the figures would need a new clause beside every one of the 16 `is_transfer`
  money queries. Silently skipping a bank row nobody saw would lose money whenever the guess is
  wrong. Ambiguous rows (two or more candidates) are held too, because no person has picked between
  the candidates.

**D4. Set-aside rows.** One table, `set_aside_rows`, holds the imported rows the app is deliberately
not counting. Each is keyed exactly as a transaction is: `dedup_hash` for a CSV row, `external_id`
for a provider row, per account. `state` is `waiting` (held, D3) or `dismissed` (a person said leave
it out, or deleted the row). `reason` is `possible_duplicate` or `deleted`. Every import path and the
sync check this table after the exact-duplicate check and before D2:
- a dismissed key is left out (the preview lists it, ticked; unticking brings it back);
- a waiting key is left alone (it is decided in Needs review).

That keeps re-imports of a statement and the sync's 5-day overlap idempotent for set-aside rows.

**D5. Undo and delete stay safe.**
- A row left out as a duplicate of an *imported* candidate links that candidate to the new import in
  `transaction_imports`, as an exact duplicate does, so undoing either import keeps it.
- A *hand-typed* candidate is never linked, so no undo can delete a row someone typed.
- Before any transaction is deleted (single delete or undo), the set-aside rows that name it as their
  candidate go back to `waiting`. Leaving out a copy can never end with neither copy counted.

**D6. Who acts.** Needs review stays household-only. Keep both: any household viewer. Delete this
one, and deleting an imported row: `canActOnOwner(attributedUserId, viewer)` (an admin, the person the
row belongs to, or anyone for a shared row). Self-scoped viewers are refused both, as import and undo
already refuse them; they still delete their own hand-typed rows. All three actions are audited.

## Owner decisions (defaults in force unless changed)

1. Sync and batch possible duplicates are **held** (not counted until Keep both). Alternative: insert
   them, flagged, and accept double counting until someone looks.
2. Imported rows can be deleted by an admin or the row's person (shared rows by anyone in the
   household). **Self-scoped viewers cannot delete imported rows.** Alternative: let them delete their
   own.
3. The suggested first sync day is the day after the newest **imported** row. Hand-typed rows are
   ignored for the suggestion and go through the duplicate check.
4. Ambiguous matches (two or more candidates) are unticked in the preview and held at sync or batch.

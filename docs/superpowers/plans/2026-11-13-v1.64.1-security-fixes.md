# Security audit pass 2 fixes — Implementation Plan (v1.64.1)

**Goal:** Close every should-fix from security audit pass 2 (`2026-11-13-security-audit-pass-2.md`) and
every minor that is cheap and app-only: make the forced password change a boundary for every action
and route, bound the password work and failed sign-ins an anonymous client can cause, bound what a
member's files and inputs can cost, stop the remaining cross-person reads for self-scoped members,
and tighten restore, audit and outbound reads. Each fix is a check the code now performs; every one
lands with a test that fails on v1.64.0.

**Base:** the v1.64.0 tag, once its gate has passed. Work on `main`, no branches or worktrees. The
orchestrator deletes `tests/_audit/` before any lane starts.

**Process:** lean. One fresh implementer per lane (five lanes, run in parallel; file sets are disjoint
except the sequenced `src/lib/loans.ts` and the test files named under Shared files). Each implementer
writes the failing test first, then the fix, and runs only: the tests it touches, every test file that
imports a module it changes (`rg -l "<module path>['\"]" tests`), `tests/ops`, and `tests/db` (lane A,
which adds the migration). Implementers do not commit; the orchestrator commits each lane by file
name, messages terse. Then ONE Opus review over the whole range, one fix round, then the release gate
once.

## Global constraints

- PUBLIC repo: no owner name, employer, Windows paths, account names or real figures. Invent every
  fixture value (people `Alex` / `Sam`, merchants `MAPLE GROCER`, `FUEL STOP 12`). No quotes of anyone
  in comments. No exploit narrative in comments, commits, docs or test names: describe the check. No
  timings, request shapes or input recipes in comments or commit messages; a regression test is named
  after the check it pins.
- Reuse the app's helpers: `requireUser`, `requireAdmin`, `userFromRequest`, `canActOnOwner`,
  `isSelfScoped`, `ownerScope`, `getWarrantyItem(id, viewer)`, `NOT_YOURS_ERROR`,
  `RULES_ARE_HOUSEHOLD_WIDE`, `appendAudit`, `sniffReceiptType`, `isModelName`, `ownRowOnly`, the
  split-person clauses (`soleOwnerClause`, `partPersonClause`). Mirror sibling actions' guards,
  messages and `ActionState` shapes.
- Every new limit is a named, exported constant beside the code that enforces it. Every refusal is a
  plain sentence that never echoes the input.
- zod only from `@/lib/zod`. `'use server'` files export only async functions; every action's first
  statement is its origin check (`tests/ops/use-server-exports`, `tests/ops/server-action-origin`).
- Tests use explicit dates, never today. Vitest 4 + Testing Library, no jest-dom. Fixtures:
  `tests/helpers/db.ts`, `tests/helpers/split-person-fixture.ts`, `tests/helpers/fake-model-server.ts`.
- Client components import nothing that reaches `@/db`. No new dependency. TypeScript 6.0.3 and Next 16
  stay pinned. App-only: no compose, Dockerfile or NAS step.
- The migration is hand-maintained like 0033: the SQL file, its `meta/_journal.json` entry and the
  `src/db/schema.ts` mirror travel together; the statement separator never appears inside a comment.
- Never `git stash`, `git checkout -- <file>` or `git restore` (CRLF rewrite breaks ops guards).

## Lane A — sign-in, sessions and the operator CLI (items 1-8)

Files: `src/lib/auth/{session,password,login,ratelimit}.ts`, new `src/lib/auth/reauth.ts`,
`src/app/(auth)/login/actions.ts`, `src/app/(auth)/change-password/{page.tsx,actions.ts}`, in
`src/app/(app)/settings/actions.ts` only `changePasswordAction`, `confirmTotpEnrollmentAction` and
`disableTotpAction`, `settings/profile-forms.tsx`, `scripts/reset-admin-password.ts`,
`drizzle/0034_auth_limits.sql` + `meta/_journal.json` + `src/db/schema.ts`, `README.md`, `INSTALL.md`.

1. **Forced password change is a boundary for every action and route.** The session join in
   `session.ts` also reads `users.must_change_password` (an internal reader; `validateSession` keeps its
   return type). `requireUser()` (and `requireAdmin()` through it) redirects a flagged user to
   `/change-password` before the caller runs; `userFromRequest()` returns null for a flagged user, so
   every route answers as signed out. A new `requireUserForPasswordChange()` is the only way to obtain
   a flagged user: the change-password page and `forcedChangePasswordAction` switch to it (the page
   keeps its redirect to `/dashboard` once the flag is clear). Logout is unchanged. The explicit
   `mustChangePassword(user.id)` checks some routes already make stay as they are. New guard
   `tests/ops/forced-password-change.test.ts`: outside `session.ts`, `validateSession` is called only
   by `api/auth/logout`, `requireUserForPasswordChange` only by the two change-password files,
   `getCurrentUser` by nobody; every route under `src/app/api` except `health` and `auth/logout` calls
   `userFromRequest`. Tests: a flagged user's import, AI and settings actions redirect and write
   nothing; the import, packs, SimpleFIN, statement-prefill, receipt-stage and stage-poll routes answer
   401; the change-password page and action still work for the flagged user and clear the flag; no
   redirect loop. Update `tests/api/export-guard.test.ts` and the flagged-user cases in
   `tests/api/warranty-receipt.route.test.ts` and `tests/api/backup-restore-upload.route.test.ts` to
   the new status.
2. **Password work limiter.** `password.ts` runs every argon2 hash and verify through one
   process-wide limiter: `ARGON2_MAX_IN_FLIGHT = 2`, the rest wait in order. Sign-in does not join a
   full line: when `ARGON2_MAX_WAITING = 8` are already waiting, `attemptLogin` (the unknown-user dummy
   verify included) returns a new `busy` result without verifying or recording an attempt, and
   `loginAction` answers `The server is busy. Try again in a moment.` A limiter refusal is never turned
   into a wrong-password result. Signed-in callers (change password, re-checks, admin create and reset,
   setup after its token check) wait their turn. Tests with a stubbed slow argon2: never more than two
   run at once; a sign-in past the waiting limit is answered busy and writes no `login_attempts` row; a
   signed-in hash waits and completes.
3. **A household-wide budget for unrecognised browsers.** `checkLockout` gains a layer: failed
   sign-ins from unrecognised browsers (`device_id` null), counted across every username, known or not,
   over `GLOBAL_WINDOW_MS` (15 minutes). At `GLOBAL_MAX_FAILURES = 100` every unrecognised browser is
   answered locked, before the user lookup or any verify, until the count falls below. A recognised
   browser keeps its own bucket and is unaffected (the v1.58.1 rule stands: a known-device cookie only
   selects a bucket). Migration `0034` adds `login_attempts_created_idx` on `(created_at)`, used by this
   count and by `purgeOldLoginAttempts`. Tests: failures spread over many unknown usernames lock the next
   unrecognised attempt; a recognised browser still signs in; a locked answer records nothing; the
   window reopens; `tests/db/migration-0034.test.ts` migrates a 0033 database and finds the index, rows
   unchanged.
4. **Re-checking the current password is counted.** New `src/lib/auth/reauth.ts`
   `verifyCurrentPassword({ user, password, headers })`: `checkLockout` for that username (with the
   browser's verified known-device id when it has one) before verifying; a wrong password is recorded as
   a failed attempt in the same buckets as sign-in; no success row is written, so a re-check never
   resets the sign-in window; while locked it verifies nothing and answers with the sign-in lockout's
   wording. Used by `changePasswordAction`, `confirmTotpEnrollmentAction` (when replacing),
   `disableTotpAction` and `forcedChangePasswordAction` (its current-password check; the
   new-equals-old check is not counted). A wrong current code in the two-factor actions is counted the
   same way. Tests per action: once the username's threshold is reached the next attempt is refused
   without a verify, even with the right password; the same failures lock sign-in from an unrecognised
   browser; a recognised browser still signs in.
5. **Turning off two-factor needs a current code.** `disableTotpAction` requires the current password
   and a current code from the existing authenticator, verified and spent with `verifyTotpCounter` /
   `consumeTotpCounter` exactly as the replace path does. The profile form gains the code field; its
   hint says a person without their authenticator asks an admin to reset two-factor. Tests: refused
   without a code, with a wrong code and with a spent code; accepted with both; other sessions end as
   before.
6. **Client address behind a proxy.** `clientIpFromHeaders` reads the rightmost valid
   `X-Forwarded-For` entry (the address the trusted proxy appended), then `X-Real-IP`, still only with
   `TRUST_PROXY=1`; an invalid rightmost entry falls through, never to an earlier entry. README and
   INSTALL (the `TRUST_PROXY` sections) say the app expects one proxy in front that appends or sets
   these headers, and that with `TRUST_PROXY=1` the app's own port should be reachable only from that
   proxy. Tests: an earlier entry is ignored; a single entry is read; an invalid last entry falls
   through to `X-Real-IP`.
7. **Reset CLI.** `npm run reset-password <username> [--clear-mfa]` reads the new password from a
   no-echo prompt on a terminal, or the first line of standard input when piped; a password given as an
   argument is refused with a line saying how to pass it. Length is checked against
   `MIN_PASSWORD_LENGTH` and `MAX_PASSWORD_LENGTH`. The reset sets `must_change_password = 1` and writes
   one `audit_log` row (action `reset_password`, entity `users`, the reset account's own id as
   `user_id` because a row needs a user, detail `Reset from the server command line`, plus
   `two-factor cleared` / `account reactivated` when true). The output says whether the account was
   reactivated, that a new password is chosen at the next sign-in, and, for a person whose sign-in is
   withdrawn, that an admin must allow sign-in first (never `They can sign in immediately`). INSTALL
   examples use the prompt (`exec -it`) and a piped form; `tests/ops/install.test.ts` still passes.
   Tests (`tests/scripts/reset-admin-password.test.ts`): argument password refused; piped password
   accepted; over-long refused; flag set; audit row written; withdrawn-sign-in message; the spawned
   script test feeds standard input.
8. **Allowed roles.** Migration `0034` also adds two triggers that refuse an insert or an update that
   sets `users.role` outside `('admin', 'member')` (SQLite cannot add a CHECK without rebuilding
   `users`). Test: another role is refused on insert and update; existing rows untouched.

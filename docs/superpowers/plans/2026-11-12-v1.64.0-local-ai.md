# Local AI, optional — Implementation Plan (v1.64.0)

**Goal:** An optional helper that asks a language model the household runs on its own network for
suggestions, and never does anything with the answer except show it. Three items, a fourth only on
the owner's yes:

1. **Settings, Connections: Local AI.** An admin enters the model server's address and a model
   name, tests it, and turns it on. Only a private (LAN) address is accepted. Off by default.
2. **Review suggestions.** For uncategorized rows that no rule and no guess covers (a big first
   import), the app asks for a category and a clean merchant name once per merchant, and Review
   shows them as an `AI suggestion` the person uses or ignores. Using one goes through the existing
   category and rename paths, including Remember for future rows.
3. **Receipt fields.** For a receipt being read on the new-item form or the bill installment form,
   the app asks for vendor, total, date and due date from the OCR text it already has, keeps only
   values actually printed on the receipt, and fills only fields the person has not typed in.
4. *(Optional, Lane E, default deferred)* **Ask in words.** A question becomes a Transactions
   filter; the page does every sum.

When AI is off, or the server is down, the app behaves as it does today: no page waits on the
server, nothing is filed, and the only sign is one line on Settings, Connections. Every item lands
with a test that fails on v1.63.0. No test talks to a real model: a fake local server stands in.

**Base:** v1.63.0 (planned in `2026-11-12-v1.63.0-year-end-and-sharing.md`). Start only after its
gate has finished and it is tagged. Work on `main`, no branches or worktrees. **One migration,
0033** (an empty `ai_suggestions` table). Line numbers below are from `main` at v1.61.0; v1.62.0
and v1.63.0 both edit the transactions page and client, `help/content.tsx` and the audit labels, and
v1.62.0 adds `src/components/review/MerchantGroups.tsx`, so re-read before editing.

**Process (lean):** one fresh implementer per lane.
- Phase 1: Lane A (migration, the `src/lib/ai/` library, scheduler, guards) runs first and alone,
  because every other lane calls what it adds. The orchestrator commits it.
- Phase 2: Lanes B (settings and docs), C (Review) and D (receipts) run in parallel. Their file
  sets are disjoint.
- Phase 3, only if the owner says build it: Lane E, after C is committed.

Implementers run the tests they touch, `tests/ops`, `tests/db` (Lane A), and every test file that
imports a module they change (`rg -l "<module path>['\"]" tests`). They do not commit; the
orchestrator commits each lane by file name. Then ONE review over the whole range, one fix round,
then the release gate once.

## Design decisions (every lane reads these first)

**L1. One protocol.** The OpenAI-compatible endpoints that both Ollama (0.5 or later) and the
llama.cpp server serve: `POST <base>/v1/chat/completions` and `GET <base>/v1/models`. Nothing else.
The chat body is `{ model, messages: [system, user], temperature: 0, max_tokens: 256, stream: false,
response_format: { type: 'json_schema', json_schema: { name, strict: true, schema } } }`. The reply
envelope is zod-checked (`choices[0].message.content` is a string), the content has at most one
surrounding ```` ```json ```` fence removed, is `JSON.parse`d (at most 8 KiB) and zod-checked against
the same shape the JSON schema describes. No Ollama-native `/api/chat` dialect (owner decision 1).

**L2. LAN only.** The base URL an admin types is normalised and checked by `normalizeLocalAiBaseUrl`:
- scheme `http:` or `https:`; no user name or password, no query, no fragment; path empty, `/` or
  `/v1` (dropped), anything else refused;
- host is one of: an IPv4 literal in 10/8, 172.16/12, 192.168/16, 127/8 or 169.254/16; an IPv6
  literal `::1`, fc00::/7 (ULA) or fe80::/10; `localhost`; a single label (`ollama`, a compose
  service name); a name ending `.local` or `.home.arpa`. Everything else is refused, 100.64.0.0/10
  included (owner decision 2), as are `0.0.0.0` and `::ffff:` mapped literals.

Every request repeats the check (`assertLocalAiUrl`, which also pins the path to the two endpoints)
and connects through `lanOnlyLookup`, an `http.request` `lookup` hook that resolves with
`dns.lookup(host, { all: true })` and refuses unless **every** address is private by the same
predicates, then connects to the address it checked, so nothing can swap the address between check
and connect. IP literals never reach the hook (Node skips lookup for them), which is why the literal
check comes first. A 3xx answer is an error (`http.request` never follows one). No `Authorization`
header, no cookie, ever. The IPv4/IPv6 predicates move verbatim from `src/lib/update/egress.ts`
(`isPrivateIpv4` ~:62, `isPrivateIpv6` ~:77) into the pure `src/lib/net/private-address.ts`, which
both guards import.

**L3. Hardening (the v1.58.1 SimpleFIN client's shape).** `LOCAL_AI_CONNECT_TIMEOUT_MS = 5_000`;
`LOCAL_AI_ANSWER_TIMEOUT_MS = 90_000` for the whole request (a cold model load can take most of a
minute); `LOCAL_AI_MAX_RESPONSE_BYTES = 1 MiB` (a declared `content-length` over it is refused before
reading, then a counting read destroys the socket past it, as `readCapped` does);
`LOCAL_AI_MAX_REQUEST_BYTES = 64 KiB`, checked before sending. Every error is the app's own sentence;
a response body is never echoed, logged or stored.

**L4. Settings, not secrets.** Keys (absence = off, the `simplefin_auto_sync` discipline):
`local_ai_enabled` (`1`), `local_ai_base_url`, `local_ai_model`, plus the state keys
`local_ai_failures`, `local_ai_last_attempt_at`, `local_ai_last_error`, `local_ai_last_ok_at`,
`local_ai_unreadable_streak`. Nothing secret is stored (no API key field, user info refused), so these
are plain `settings` rows; nothing is encrypted because there is nothing to encrypt (owner decision 3).
Turning it on, changing it, turning it off and forgetting suggestions each append one audit row.

**L5. Two kinds of failure.**
- *The server* (connect refused or reset, name not found, a lookup refused by L2, timeout, any 3xx,
  401/403, 404, 400, 5xx, an oversize or non-OpenAI-shaped reply, or 5 unreadable answers in a row):
  record a failure, drop the rest of the queue, wait `min(5 min x 2^(n-1), 6 h)` from the last
  attempt (`localAiBackoffMs`, the `autoSyncBackoffMs` shape). A success clears the count.
- *One answer* (content not valid JSON, not the schema, or nothing in it survives L7's checks): that
  merchant or receipt is recorded `failed` and the queue continues.

While off or waiting (`localAiActive(now)` false): no request is made, the receipt poll reports AI as
off, and Review shows only suggestions already stored (they need no server; owner decision 7).

**L6. What is asked, and nothing more.**
- *Merchant job:* the household's non-archived categories as labels (`Parent > Child`, made unique),
  and one row: the newest queued row of that merchant, its raw description (at most 200 characters),
  signed amount with `money out` / `money in`, and date. Never an account name, a person, a note,
  another row, or another merchant.
- *Receipt job:* the staged receipt's OCR text (first 6,000 characters) and the household's today.
- *Test button:* made-up data only (`MAPLE GROCER 0042`, -42.17, 2026-03-09, categories `Groceries`,
  `Dining out`); no household data leaves on a test.

**L7. What comes back, and what is kept.**
- *Merchant:* `{ category: <one of the labels> | null, merchant: string (<= 60) | null }`. The label
  maps back to its id; the name passes `cleanMerchantName` (control characters stripped, spaces
  collapsed, 2+ letters, no `://`, `www.` or `@`, not the same as the raw text ignoring case and
  spaces). Stored per merchant in `ai_suggestions`.
- *Receipt:* `{ vendor, total, purchaseDate, dueDate }`, each nullable. Grounded: `total` must equal a
  figure printed in the text (`currencyFigures`) and stay under `MAX_SUGGESTED_PRICE_CENTS`; each date
  must be a date printed in the text (`printedDates`) inside the bounds `suggestPurchaseDate` and
  `suggestDueDate` already use; `vendor` needs a word of 3+ letters that appears in the text (case- and
  accent-folded) and at most `MAX_VENDOR_CHARS`. A field that fails is dropped; the rest are kept.
  Stored in an AI sidecar file beside the OCR sidecar (`<stagingId>.ai.json`), swept with it.

**L8. Who is asked about.** The AI targets merchants with at least one row that is in the review
queue, uncategorized and unsplit (`and(REVIEW_WHERE, UNCATEGORIZED_WHERE)`, engine.ts ~:2135, :2174),
with a non-empty `normalized_merchant`, no `ai_suggestions` row yet, and no Always ask rule
(`alwaysAskRuleFor`; engine.ts ~:161 gives such a merchant no guess either). A Bayes guess (category
set, source `bayes`) or a rule already covers the rest. Most rows first, then newest. One call per
merchant, not per row (owner decision 5).

    are private to `transactions/actions.ts`. So C1 calls the actions, as `acceptAllGuessesAction` calls
    `acceptGuessAction`, and no lane edits that file.
- Categories are never hard-deleted (archive only), so the `ai_suggestions.category_id` reference cannot
  block a delete.
- `README.md` (~:9) and `INSTALL.md` (~:4) both say `three opt-in exceptions`.

## Not in this release

- AI on receipts already attached to an item (no suggestion surface exists for them).
- One button that accepts every AI suggestion at once. The merchant view is the fast path: one decision
  per merchant, seeded by the suggestion.
- Different suggestions for one merchant by amount (fuel against groceries at one store). Bounded rules
  (v1.39.0) still do that by hand.
- API keys, cloud or paid services, HTTPS with a self-signed certificate (Node's default checks refuse
  it; plain http on the LAN works), streaming answers, and pulling or managing models.
- Ask in words, unless the owner opts in (Lane E).

## Owner decisions (defaults in force unless changed)

1. **One protocol:** the OpenAI-compatible `/v1/chat/completions` and `/v1/models`, which Ollama 0.5+
   and llama.cpp's server both serve. No Ollama-native `/api/chat`.
2. **Accepted addresses:** private IPv4 (10/8, 172.16/12, 192.168/16), loopback, link-local, IPv6
   ULA, `localhost`, one-word names and `.local` / `.home.arpa` names, every name checked at each
   request to resolve only to those. **Tailscale and carrier NAT addresses (100.64.0.0/10) are
   refused**; say so if the model server is reached over Tailscale and the range is added.
3. **No API key field.** Nothing secret is stored, so nothing is encrypted.
4. **Remember for future rows is ticked by default** on an AI suggestion, as a review-mode pick and the
   merchant view already teach. Alternative: unticked.
5. **One suggestion per merchant**, from its newest uncategorized row; Always ask merchants are never
   asked about; Ignore lasts until `Forget all AI suggestions`.
6. **Receipts:** AI fills only empty, untouched fields, except the vendor, where it replaces the
   pattern guess if nobody touched it. The pattern total and dates win when found. AI values must be
   printed on the receipt.
7. **While the server is down**, suggestions already made still show (they need no server); nothing new
   is asked; Settings shows the waiting line. Alternative: hide them too.
8. **Ask in words (Lane E) is deferred**; it is built only on the owner's yes.
9. **Both README and INSTALL** change `three` to `four opt-in exceptions` and name the LAN-only helper, so
   neither doc understates what the app can reach.
10. **Limits:** 5 s to connect, 90 s per answer, 1 MB per reply, 64 KB per request. Backoff 5 minutes
    doubling to 6 hours. 100 merchants per sweep, one request at a time.

## Review focus (one Opus review)

- No byte leaves except to the configured LAN address. The address and every resolved address are
  checked on each request and the checked address is the one connected to. Redirects are refused; the
  caps and timeouts hold. No key, cookie or reply body leaves the client or lands in a log, a setting or
  the audit.
- Off and unreachable are today's app:
  - no page waits on the server;
  - the poll route's done answer differs only by `ai: off`;
  - Review's props with AI off equal v1.63.0's;
  - the OCR tree is untouched.
- Suggestion only. Nothing in `src/lib/ai/` files a row or writes a rule. Use goes through
  `setCategoryAction` / `renameTransactionAction` with every existing guard: archived, Always ask,
  rule ownership, split, self viewer.
- Prompts carry one row or one receipt, plus the household's non-archived category labels. Self viewers
  never receive a suggestion or reach Review. A staged receipt's AI result reaches only its uploader.
- Receipt values are grounded in the printed text; a typed field is never changed; pattern totals and
  dates are kept.
- Backoff cannot hammer a down server. The queue is bounded. A failed merchant is not re-asked every
  tick. Each settings change is audited once, with no secret in the detail.
- Migration 0033's shape and CHECKs. The guards are extended, not loosened, and the Watchtower predicate
  move changes no result.

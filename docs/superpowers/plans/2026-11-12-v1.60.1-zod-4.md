# zod 4 — Implementation Plan (v1.60.1)

**Goal:** Close the open high Dependabot alert on `zod` (GHSA-mrhx-c7xc-m3w5, "Zod can exhaust memory
while validating oversized constrained collections", vulnerable `< 4.6.6`, patched only in 4.6.6; no
3.x fix exists) by moving from 3.25.76 to the 4.x line, with no change anyone can see: every form,
server action and API route accepts the same input, refuses the same input, and shows the same words
when it refuses. The app shows `issues[0].message` to people in 39 places and in two pack-import
errors, and most of those messages are zod's own defaults, which zod 4 rewords. So the core of this
release is one module, `src/lib/zod.ts`, that every file imports zod from and that installs zod 3's
English wording as zod 4's global error map. Two characterization tests are committed on zod 3
before the bump. They pin today's messages, and they must still pass unchanged after it.

**Base:** v1.60.0 (the tag the v1.60.0 release lands on). Work on `main`, no branches or worktrees.
Start only after v1.60.0's gate has finished: Lane A runs `npm install`, which rewrites
`node_modules` under anything else running.

**Target version:** `"zod": "^4.6.7"` (latest 4.x, published 2026-10-12; 4.6.6 on 2026-10-11).
`npm ls zod` today shows one copy, the app's own. No package pins zod 3: drizzle-kit bundles its own
copy into its dist, drizzle-orm and jiti list zod as a devDependency only, and Next ships a compiled
copy of its own. So the lock changes in one `node_modules/zod` entry plus the root dependency line,
and no `overrides` entry is needed.

**Process (lean):** one fresh implementer per lane. Lane A runs first and alone, in two steps: step 1
is the characterization tests on zod 3 (orchestrator commits), step 2 is the bump plus the
compatibility module (orchestrator commits). Then Lanes B-E run in parallel. Their file sets are
disjoint, by directory. Each converts its files, then runs its touched tests, `tests/ops`, and every
test file that imports a module it changes (`rg -l "<module path>['\"]" tests`). Implementers do not
commit; the orchestrator commits each lane by file name. Then ONE review over the whole range, one fix
round, and the release gate once.

**Sources:** the zod 4 migration guide (https://zod.dev/v4/changelog), fetched 2026-11-12. Every
claim in the table below was then re-checked two ways:

- the app's schema shapes, plus the inputs listed under Lane A, were run under 3.25.76 (the installed
  copy) and 4.6.7 (the published package, unpacked into a scratch directory) side by side;
- `tsc` (TypeScript 6.0.3) was run over `src`, `tests` and `scripts` against 4.6.7's types. It gives
  exactly two errors, both `errorMap`.

## Global constraints

- PUBLIC repo: no owner name, employer, Windows paths, account names or real figures. Invent every
  fixture value (people `Alex` / `Sam`, merchants like `MAPLE GROCER`). No quotes of anyone in
  comments.
- App-only: no compose, Docker, install-script or operator-doc changes, and nothing the owner must
  test. No migration.
- `'use server'` files export only async functions, and every action's first statement stays its
  origin check (`tests/ops/use-server-exports`, `tests/ops/server-action-origin`). This release
  changes imports and schema literals only, never the order of an action's statements.
- No existing test changes. `git diff v1.60.0 -- tests` may add files and lines, but its only removed
  or changed lines are the version pin in `tests/ops/docker.test.ts`. If an existing assertion fails,
  fix the code, not the test.
- Tests use explicit dates (`warrantyInputSchema('2026-03-15')`, never today). Vitest 4 + Testing
  Library, no jest-dom.
- Never `git stash`, `git checkout -- <file>` or `git restore` (a CRLF rewrite breaks the ops guards).
- TypeScript 6.0.3 and Next 16 stay pinned. Write the lock with npm 10:
  `npx -y npm@10.9.9 install zod@^4.6.7`, then `npx -y npm@10.9.9 ci --ignore-scripts --dry-run` must
  pass (CI runs npm 10.9.9).

## Zod 3 -> 4 changes that touch this code (verified)

Eight changes matter here. Five change behaviour and need code (1-5); three are deprecations or
runtime defaults, converted so the ops guard can stay simple (6-8).

1. **`errorMap` is dropped (renamed `error`).** It does not compile, and at runtime it is ignored, so
   the custom message disappears. There are 2 sites: `src/app/(app)/settings/backups/actions.ts:49`
   (`z.literal('on', { errorMap: () => ({ message: 'Tick the confirmation box first.' }) })`) and
   `src/lib/warranty/items.ts:277` (`.enum(BILLING_CYCLES, { errorMap: ... 'Billing must be Monthly or
   Annual.' })`). Fix: `{ error: '<same text>' }`. Verified: under zod 4, an `error` string on the
   schema replaces every issue that schema raises, including a non-string input (`5` to the billing
   enum gives the billing sentence), exactly as the zod 3 errorMap did. `invalid_type_error` and
   `required_error` are not used anywhere.
2. **Every default message is reworded.** For example, `String must contain at most 80 character(s)`
   becomes `Too big: expected string to have <=80 characters`, `Required` becomes
   `Invalid input: expected string, received undefined`, and `Invalid email` becomes
   `Invalid email address`. Every enum, literal and number-range message changes the same way. These
   messages reach people through `parsed.error.issues[0]?.message` at:
   - `import/actions.ts` :55, :116, :180;
   - `settings/accounts/actions.ts` :74, :185;
   - `settings/actions.ts` :105, :142, :161, :232, :541, :567, :657;
   - `settings/backups/actions.ts:77`;
   - `settings/item-types/actions.ts` :31, :53, :73;
   - `settings/managers/actions.ts:51`;
   - `settings/merchant-rules/actions.ts:336`;
   - `settings/notifications/actions.ts:155` (`firstIssue`, used 6 times);
   - `settings/users/actions.ts` :42, :83, :123;
   - `transactions/actions.ts` :465, :949, :1150, :1431;
   - `warranties/actions.ts` :467, :502, :902;
   - `(auth)/change-password/actions.ts:42`, `(auth)/setup/accounts/actions.ts:44`,
     `(auth)/setup/actions.ts:48`;
   - `api/import/batch/commit/route.ts:75`, `api/import/commit/route.ts:45`,
     `api/import/preview/route.ts:109`, `api/import/raw-preview/route.ts:52`,
     `api/warranties/receipts/stage/route.ts:108`;
   - `src/lib/packs.ts` :447, :484 (`This rules pack is malformed: <message>.`).

   Defaults that people can actually reach include: every unlabelled `.max(80)` on names and
   institutions; notifications' port and knob ranges, `fromEmail` and `destination` (`Invalid email`)
   and `username`/`fromName` `.min(1)`; enum fields; pack fields; and the import routes' `stagingId`
   (`Invalid uuid`). No existing test pins a single default message (rg for `String must contain`,
   `Number must be`, `Invalid enum value`, `Required` and the rest finds none). Fix: one global map
   (Lane A).
3. **`.uuid()` is now strict RFC 9562** (version nibble 1-8, variant 8-b).
   `11111111-2222-3333-4444-555555555555` passes on zod 3 and fails on zod 4. There are 5 sites:
   - `src/app/(app)/import/actions.ts:41`;
   - `src/app/api/import/batch/commit/route.ts:29`;
   - `src/app/api/import/commit/route.ts:14`;
   - `src/app/api/import/preview/route.ts:14`;
   - `src/app/api/import/raw-preview/route.ts:18` (and its comment at :13).

   Fix: `z.guid()`, whose pattern equals zod 3's `.uuid()` and `UUID_RE` in
   `src/lib/import/staging.ts:25`, the real path guard. Its issue maps back to `Invalid uuid`.
4. **A thrown ZodError's `.message` is a JSON dump in both versions, in different shapes.** zod 4
   writes `origin` first and drops `type` and `exact`. Four catch blocks show `error.message` for an
   error that can be a ZodError thrown by a lib `.parse()`:
   - `src/app/(app)/goals/actions.ts:48`: `createGoal`, reachable with a name of only spaces;
   - `src/app/(app)/transactions/actions.ts:230`: `createManualTransaction`, a description of only
     spaces or over 300 characters;
   - `src/app/(app)/settings/accounts/actions.ts:88` and `src/app/(auth)/setup/accounts/actions.ts:58`:
     `createAccount`, reachable only with an owner id of `0` in a crafted request.

   The zod 3 text cannot be kept. See owner decision 1. The default: these four show the first issue's
   message through `errorText()` (Lane A), as `settings/item-types/actions.ts:31` already does.
5. **`.int()` accepts safe integers only, and `z.number()` refuses `Infinity`.** zod 3 accepted
   `1e300` or `9007199254740993` on `z.coerce.number().int().positive()` and on `z.number().int()`
   amount fields. zod 4 refuses them (`too_big`, maximum 9007199254740991), and through the map the
   refusal reads `Number must be less than or equal to 9007199254740991`. `Infinity` on an `.int()`
   field was already refused, and the map keeps that message (`Expected integer, received float`).
   A plain `z.number()` with no `.int()` refuses `Infinity` now. That shape exists only in
   `src/lib/warranty/staging.ts` :51-56 and `src/lib/backup/restore.ts` :90-98, which read JSON files,
   and JSON cannot carry `Infinity`, so it is unreachable. See owner decision 2.
6. **Deprecated, still working, converted:**
   - `z.string().email()` becomes `z.email()` at `settings/notifications/actions.ts` :75, :102, :129.
     The 4.6.7 regex is not the 3.x one, but on 25 edge cases (leading, trailing and double dots,
     apostrophes, plus signs, hyphens, bad TLDs, case, a trailing newline) both accept and refuse
     identically. The check order is unchanged too: an invalid address longer than 254 characters
     still reports `Invalid email` first.
   - `z.ZodIssueCode.custom` becomes `'custom'` at `src/lib/import/mapping.ts` :91, :95,
     `src/lib/packs.ts` :316, :331 and `src/lib/warranty/items.ts` :328, :337, :343.
   - The `message:` key in schema params becomes `error:` at:
     - `budgets/actions.ts` :46, :49;
     - `goals/actions.ts:22`;
     - `settings/backups/actions.ts` :46-48;
     - `settings/merchant-rules/actions.ts` :113-114, :330-331;
     - `settings/notifications/actions.ts` :80-81;
     - `transactions/actions.ts` :457, :692, :1403, :1410-1411.

     Leave string shorthands (`.min(1, 'Name is required')`, `.refine(fn, 'msg')`) alone; they are
     not deprecated.
7. **Messages are computed when read, and the map's precedence works for us.** In 4.6.x the global
   `customError` runs when `.message` is first read, and only when the schema gave no message of its
   own: a message on the check or the schema wins, then a per-parse map, then the global map, then the
   locale. So every explicit message in the code stays as written, and only defaults go through the
   map. `z.config` is process-global per zod copy, which is why a stray direct `import 'zod'` would
   still get the map in a test that loads `@/lib/zod` anywhere. That makes a structural guard
   necessary: the ops test, not the parity tests, enforces the single import.
8. **The JIT probe under the CSP.** zod 4 compiles object parsers with `new Function`, after a probe.
   The app's CSP (`src/lib/auth/security-headers.ts:16-17`) has no `'unsafe-eval'`, so in a browser
   the probe would file a `securitypolicyviolation` report. No client component parses a schema today
   (client files import types only from zod-using modules). Set `jitless: true` anyway: one line, no
   change in results, and it keeps the server eval-free too.

The advisory itself: with `.max()` on an array, 4.6.6+ refuses before it walks the elements. A
2,000,000-item body against `.max(3)` gives 2,000,001 issues in 3.25.76 and 1 issue in 4.6.7, and
`issues[0]` is the same `too_big` in both. In this app that covers: the batch commit body
(`files ... .max(MAX_BATCH_FILES)`), dashboard `importIdsField`, warranties `stagedSchema`, and the
pack arrays.

**Not affected (verified; no work planned):**

- `.default()` (accounts.ts:54, mapping.ts:82/:86, items.ts loanDirection, raw-preview `encoding`,
  undo `confirm`): every default is a constant of the output type, with nothing parsed after it, so
  zod 4's short-circuit gives the same value. No `.prefault()` is needed.
- `z.preprocess` (`optionalText`, items.ts:236): the same output, including a missing key (`Required`),
  a blank value (null) and an over-length value.
- packs' `.optional().transform(v => v ?? null)` on absent keys: the same output.
- A missing key on a `z.coerce` field: the same `Expected number, received nan` through the map.
- Every union and `.or()`: connections :52, transactions :1354, simplefin link :10, restore :111,
  notifications :93/:97/:125 all give the same `issues[0]`.
- `.superRefine` with `path`: not deprecated in 4.6.7, and field issues still come first.
- `.issues`: the code uses it everywhere and `.errors` nowhere (`.errors` is removed in 4).
- `z.infer`: one site, transactions :524. The `z.ZodType<ImportMapping>` cast at mapping.ts:99 and
  `z.ZodError` in notifications :154 and item-types :31 all still compile, and `instanceof
  z.ZodError` holds.
- Not used anywhere: `.format`/`.flatten`/`.formErrors`, `.strict`/`.passthrough`/`.merge`,
  `z.record`, `.nonempty`, `nativeEnum`, `z.function`, `z.promise`, `.ip`, `.url`, `z.date`,
  `ctx.path`, `fatal`.
- `z.coerce` input type is now `unknown`. Nothing reads `z.input<>`, and `tsc` is clean apart from
  item 1.

```ts
// The one place the app imports zod. zod 4 rewords every default message; this keeps zod 3's
// English for the issue kinds this app's schemas raise (tests/lib/zod-compat.test.ts pins them),
// and returns undefined for anything else so zod 4's own wording applies.
import { z } from 'zod';

type Inst = { _zod?: { def?: { type?: string; checks?: Array<{ _zod: { def: { check?: string; format?: string } } }> } } };

function v3Type(data: unknown): string {
  if (typeof data === 'number') return Number.isNaN(data) ? 'nan' : 'number';
  if (typeof data !== 'object') return typeof data;
  if (data === null) return 'null';
  if (Array.isArray(data)) return 'array';
  if (data instanceof Date) return 'date';
  if (data instanceof Map) return 'map';
  if (data instanceof Set) return 'set';
  return 'object';
}
const joinValues = (values: readonly unknown[]) => values.map((v) => (typeof v === 'string' ? `'${v}'` : String(v))).join(' | ');
const size = (origin: string) => (origin === 'int' ? 'number' : origin);
const isIntField = (inst: Inst | undefined) =>
  (inst?._zod?.def?.checks ?? []).some((c) => c._zod.def.check === 'number_format' && c._zod.def.format === 'safeint');

export function zod3Message(iss: z.core.$ZodRawIssue): string | undefined {
  const inst = iss.inst as Inst | undefined;
  switch (iss.code) {
    case 'invalid_type': {
      if (iss.expected === 'int') return 'Expected integer, received float';
      // +-Infinity on an .int() field: zod 3 let z.number() through and failed it at .int().
      if (iss.expected === 'number' && typeof iss.input === 'number' && !Number.isNaN(iss.input) && isIntField(inst)) {
        return 'Expected integer, received float';
      }
      const received = v3Type(iss.input);
      return received === 'undefined' ? 'Required' : `Expected ${iss.expected}, received ${received}`;
    }
    case 'invalid_value': {
      const type = inst?._zod?.def?.type;
      if (type === 'literal') return `Invalid literal value, expected ${JSON.stringify(iss.values[0])}`;
      if (type !== 'enum') return undefined;
      if (typeof iss.input === 'string') return `Invalid enum value. Expected ${joinValues(iss.values)}, received '${iss.input}'`;
      const received = v3Type(iss.input);
      return received === 'undefined' ? 'Required' : `Expected ${joinValues(iss.values)}, received ${received}`;
    }
    case 'too_small': {
      const k = size(iss.origin);
      if (k === 'array') return `Array must contain ${iss.exact ? 'exactly' : iss.inclusive ? 'at least' : 'more than'} ${iss.minimum} element(s)`;
      if (k === 'string') return `String must contain ${iss.exact ? 'exactly' : iss.inclusive ? 'at least' : 'over'} ${iss.minimum} character(s)`;
      if (k === 'number') return `Number must be ${iss.exact ? 'exactly equal to ' : iss.inclusive ? 'greater than or equal to ' : 'greater than '}${iss.minimum}`;
      return undefined;
    }
    case 'too_big': {
      const k = size(iss.origin);
      if (k === 'array') return `Array must contain ${iss.exact ? 'exactly' : iss.inclusive ? 'at most' : 'less than'} ${iss.maximum} element(s)`;
      if (k === 'string') return `String must contain ${iss.exact ? 'exactly' : iss.inclusive ? 'at most' : 'under'} ${iss.maximum} character(s)`;
      if (k === 'number') return `Number must be ${iss.exact ? 'exactly' : iss.inclusive ? 'less than or equal to' : 'less than'} ${iss.maximum}`;
      return undefined;
    }
    case 'invalid_format':
      if (iss.format === 'regex') return 'Invalid';
      if (iss.format === 'email' || iss.format === 'url') return `Invalid ${iss.format}`;
      if (iss.format === 'guid' || iss.format === 'uuid') return 'Invalid uuid';
      return undefined;
    case 'invalid_union':
    case 'custom':
      return 'Invalid input';
    default:
      return undefined;
  }
}

z.config({ jitless: true, customError: zod3Message });

export { z };

/** A thrown error as one line for a form. A ZodError's own .message is a JSON dump. */
export function errorText(error: unknown, fallback: string): string {
  if (error instanceof z.ZodError) return error.issues[0]?.message ?? fallback;
  return error instanceof Error ? error.message : fallback;
}
```

## Owner decisions

1. **ZodError dumps (item 4).** In four catch blocks a blank goal name, a blank quick-add description
   or a crafted owner id shows a block of JSON today, and zod 4 changes that block's shape. Default:
   show the first message instead (`Name is required`), as item-types already does, listed under
   Fixed. Alternative: leave it, and the JSON shape changes.
2. **Integers past 2^53 and Infinity (item 5).** zod 4 refuses ids and amounts above
   9,007,199,254,740,991 (about $90 trillion in cents), which zod 3 accepted but the app could not
   store exactly. Default: accept the refusal, with the message
   `Number must be less than or equal to 9007199254740991`.
3. **Range.** Default `^4.6.7`. The compat test catches a later 4.x that changes issue shapes.

# v1.24.0 backlog — three items, logged before any code was written

Same discipline as the v1.21.0 backlog: record the ask in the household's own words, what
was verified in the code, the decision, what was rejected, and the traps waiting for
whoever implements it. Written 2026-09-01, before either lane started.

---

## Item 1 — the review queue calls itself "Transactions"

**Ask.** "Review page still says trasaction. can we change that its confusing?"

**Verified.** `src/app/(app)/transactions/transactions-client.tsx` renders
`<PageHeader title="Transactions" ... />` unconditionally, while the `PageGuide`
immediately below it already branches on `reviewMode`. Review was folded into this page in
v1.16.0 (Lane C item 3) and the guide was ported across; the header was not.

**Decision.** Header follows `reviewMode`:

- review: **Needs review** / "Transactions the rules could not settle on their own. Pick a
  category to clear each one."
- otherwise: unchanged.

**Trap.** `tests/ops/onboarding-coverage.test.ts` greps this file's *source* for the
literal `<PageGuide`, so a conditional render still satisfies it — but any test asserting
the literal heading text has to be updated with an argument, not weakened.

## Item 2 — hide-transfers is a one-way door

**Ask.** "Trasnaciton page has a check hide trasnfers i need to imporove on this. Can we
somehow have a filter what user can use to, show only transfers, hide trasnfers, all data?
currently once i apply a trasnfer its hard to find that data again"

**Verified.** Two states only. `TransactionFilter.includeTransfers?: boolean`, and the
clause fires only on an explicit `false`. The control is a checkbox living *behind the
collapsed filter disclosure*.

The last sentence of the ask is the real defect, and it is worse than a missing filter.
`REVIEW_WHERE` excludes transfers unconditionally, so a **mis-tagged** transfer leaves the
review queue *and* the default list at the same moment. There is currently no route back to
it from either screen. "Transfers only" is not a convenience; it is the recovery path for a
mistake the app makes easy to commit.

**Decision.** One three-state field, `transferView: 'all' | 'only' | 'none'`, replacing
`includeTransfers` outright — no compatibility shim. URL contract stays backwards
compatible: absent = all, `transfers=0` = none (existing links keep their meaning),
`transfers=only` = only. The control becomes three always-visible segmented links, not a
checkbox behind a disclosure — burying it is what made transfers unreachable. Hidden in
review mode, where `REVIEW_WHERE` would make it a lie.

**Rejected.** Keeping `includeTransfers` alongside the new field. Every symptom in the
v1.20–v1.23 cycle traced back to one idea carrying more than one implementation.

## Item 3 — deleting a rule leaves its damage behind

**Ask.** "when we add a merchange rule and reapply if user messes up the transactions get
updated. user deletes the rule but nothing gets fixed. would it be possible to have a
option called delete rule another delete rule and unapply rule from trasnctions?"

Then, narrowing it: "no i dont want to do undo want want to tell user that there is no undo
delete of rule. we can set those trasnactions as un categorized. can we date date range on
this... also date date should be on re apply logic tyoo." And: "renames can we be all
renames thats fine... we dont have to show dates on rename rules."

**Verified.**

- Rename rules **already** revert on delete — `deleteRuleAction` routes them to
  `deleteRenameRule`, which calls `applyRenameRules` and clears every row the rule set.
  The behaviour exists; only the dialog was missing.
- Every other kind calls bare `deleteRule(id)`. Transactions keep what the rule gave them.
- `categorization_source` is `'rule' | 'bayes' | 'manual' | 'none'` — it records **that** a
  rule acted, never **which** rule. `categorizeTransaction` returns a `matchedRuleId` but
  it is transient. So attribution must be derived, and the only correct place to derive it
  from is `ruleImpactCounts`, which is already what the "Affects" column displays. Using a
  second definition would let a dialog state a number the action does not honour.

**Decisions.**

1. **No undo, and say so.** No pre-rule category is recorded anywhere, so none can be
   restored. The dialog states that as a fact rather than offering a way back.
2. **Clearing means uncategorized** — `category_id = NULL`, source `'none'`, confidence
   NULL, which returns the row to the review queue.
3. **Do not re-run other rules after clearing.** Literal reading of "set those transactions
   as un categorized". An automatic re-run would let a second rule immediately recategorize
   the rows, so the button would appear to have done nothing.
4. **Date range on clearing: category and transfer only, never rename.** A partial rename
   revert leaves rows carrying a `display_description` whose rule is gone, and the next
   `applyRenameRules` pass clears them anyway — a bounded revert silently unwinds later.
   All-or-nothing is the only stable shape. A bounded **re-apply** is safe for both kinds,
   because re-applying only ever adds.
5. **Renames are reversible in fact.** The bank text lives in `description`; a rename only
   ever wrote `display_description`. So "cannot be undone" attaches to deleting the rule
   and to clearing categories — never to a rename revert. Copy has to say the true thing
   per kind rather than carrying one blanket warning.
6. **`not_transfer` gets no clear option.** "Clearing" one would mean re-flagging rows *as*
   transfers, a stronger claim than reverting, and it moves money out of every report.
7. **Every confirm is a `RowDialog`** — the shared blurred shell used by notes and splits.
   Third time this cycle that the idiom had to be corrected after the fact; the rule now
   lives in `RowDialog`'s own docblock.

**Trap for the implementer.** Clear *before* deleting the rule. Attribution resolves
`matchedRuleId` by simulation, which needs the rule to still exist.

**Trap on copy.** The "your manual choices are not touched" sentence must be written from
what `ELIGIBLE` and `applyRenameRules`' precedence comment actually do. Never adjust the
code to match copy already written.

# Faster review and month check-in — Implementation Plan (v1.62.0)

**Goal:** Make clearing Needs review a handful of decisions instead of one per row, make a wrong bulk
press cheap to take back, and replace the straight-line pace with a month figure that knows about
bills and recurring charges. Four items:

1. **Review by merchant.** The queue groups by merchant; one decision (category, person, transfer,
   recurring) files every queued row of that merchant, under the rule-writing rules the app already
   has.
2. **Transfer-pair suggestions.** Equal and opposite amounts on two household accounts within 3 days
   are offered as a pair; one tap marks both; a dismissal is remembered.
3. **Undo the last bulk change.** Per person, the most recent bulk change, for 15 minutes, restoring
   the rows, the rules it wrote or removed, and the categorizer's training, with an audit row.
4. **Month check-in.** Budgets and the Dashboard show spent so far, plus bills and marked recurring
   charges still due this month, plus what is usually spent in the rest of the month. A rent payment
   on the 1st no longer projects as several times its limit on the 7th.

Every item lands with a test that fails on v1.61.0.

**Base:** v1.61.0 (planned in `2026-11-12-v1.61.0-no-double-counting.md`). Start only after its gate
has finished and it is tagged. Work on `main`, no branches or worktrees. **No migration:** undo
records and pair dismissals live in `settings`, as insight dismissals and the sync backoff do, so
0032 stays unused. Line numbers below are from v1.60.x; v1.61.0 moves some of them (it edits the
transactions page, client, actions, filter-params, `transactions.ts`, the dashboard, `audit.ts` and
`tests/ops/attribution-writers.test.ts`), so re-read before editing.

**Process (lean):** one fresh implementer per lane.
- Phase 1: Lanes A and D run in parallel. Their file sets are disjoint.
- Phase 2: after A is committed, Lanes B and C run in parallel. Both call A's exports.
- Item C4 (one mount) runs only after B is committed.

Implementers run the tests they touch, `tests/ops`, and every test file that imports a module they
change (`rg -l "<module path>['\"]" tests`). They do not commit; the orchestrator commits each lane
by file name. Then ONE review over the whole range, one fix round, then the release gate once.

## Lane A — bulk undo library (item 3 foundations; phase 1, with D)

Files: `src/lib/bulk-undo.ts` (new), `src/lib/categorize/rules.ts`, `src/lib/audit.ts`; tests
`tests/lib/bulk-undo.test.ts` (new), `tests/lib/audit.test.ts`, `tests/ops/rule-authoring-intent.test.ts`,
`tests/ops/attribution-writers.test.ts`; run `tests/ops/visibility-invariants.test.ts` unchanged.

**Scope decision (why last-only, per person, 15 minutes).** Undo exists for the wrong pick noticed
at once, on the screen where it was made. Within 15 minutes, later imports, engine runs and other
members rarely touch the same rows, so a faithful restore is almost always possible. Past that, a
restore would often have to refuse. Last action only, because two stacked undos over overlapping
rows need an ordering model the app does not have. Per person, so one member's undo can never
reverse another member's work.

A1. **Rule snapshots stay behind `rules.ts`** (the merchant_rules table rule, R-05).
   - `exactRuleRows(patterns, kinds)` returns every column of the exact rules for those patterns.
     It reads enabled and disabled rules alike, for kinds `category`, `transfer`, `not_transfer`,
     `attribution`, `recurring` and `not_recurring`. Every bulk path writes exact rules only
     (`confirmCategory`, `teachTarget`, `setTransferFlag`, `setRecurringMarks`).
   - `restoreExactRules({ before, createdIds })` runs in one transaction:
     - deletes `createdIds`;
     - re-inserts a `before` row that no longer exists, with its original id and every column (the
       housekeeping `deleteExactRule` case, engine.ts ~:1710);
     - writes back every column of a `before` row that still exists (a teach that changed a
       bounded rule's category, a re-enable).

     It returns `{ removed, restored }`.
A2. **`src/lib/bulk-undo.ts`.**
   - Constants `BULK_UNDO_MINUTES = 15` and `BULK_UNDO_MAX_ROWS = 2000`. Settings key
     `bulk_undo:<userId>`, a JSON value with `v: 1`. `BulkUndoKind` is `'categorize' | 'transfer' |
     'person' | 'recurring' | 'transfer_pair'`.
   - `captureBulkBefore({ ids, merchants? })` makes one read of the rows (`id, normalized_merchant,
     category_id, categorization_source, confidence, is_transfer, attributed_user_id`). It also
     reads `exactRuleRows` for their merchants plus `merchants` (trimmed and uppercased as
     `setRecurringMarks` does), the ids that already have a `loan_payments` link, and the merchants
     an enabled Always ask rule covers. Over `BULK_UNDO_MAX_ROWS` it returns `{ tooLarge: true }`.
   - `recordBulkUndo({ userId, kind, label, before, at })` reads the same after-state and keeps only
     the rows and rules that changed. For each changed row it records the Bayes pair
     `confirmCategory` made:
     - *trained*: the new category, when the row became `manual` and the merchant is not Always
       ask;
     - *untrained*: the old category, when the row was `manual` with a category.

     It also records loan links the action added (`source = 'rule'`, from `applyPaymentMatchers`
     inside `confirmCategory`). It writes the record with `expiresAt = at + 15 min`. When nothing
     changed it writes nothing and leaves the previous record. `tooLarge` deletes the user's record
     and returns `'too_large'`, so Undo never names an older action than the latest one.
   - `lastBulkUndo(userId, now)` returns `{ label, rows, expiresAt }` or null. It deletes an expired
     record when it reads one.
   - `undoLastBulkAction({ viewer, now })` refuses in these cases, each with nothing written:
     - no record, or an expired one: `That change is more than 15 minutes old, so it can no longer
       be undone.`;
     - a self viewer when any recorded row is no longer theirs (`transactionOwners` +
       `ownerScope`): `NOT_YOURS_ERROR`;
     - stale: a recorded row is gone, or its tracked columns differ from the recorded after-state,
       or a recorded rule differs from its after-state (created rule changed or gone, removed rule
       back, modified rule changed again): `Something in that change was edited since, so it cannot
       be undone. Nothing was changed.`

     Otherwise, in one db transaction, it:
     - restores the row columns (`updated_at` = now);
     - reverses Bayes (`untrain` trained, `train` untrained, the mirror of `confirmCategory`'s pair);
     - calls `restoreExactRules`;
     - unlinks the added loan links through `unassignTransactionFromLoan` (loans.ts ~:2366);
     - deletes the record and appends the audit row (A3).

     A thrown FK or constraint error rolls everything back and returns the stale refusal. It
     returns `{ ok: true, rows, rulesRemoved, rulesRestored }`.
A3. **Audit.** `AuditAction` (audit.ts ~:20) gains `'undo_bulk_action'` (no migration: the column
   has a LENGTH check, not an enum). Entity is `transactions` with the smallest restored id, or
   `merchant_rules` with the smallest rule id for a rules-only undo. Detail reads `Undid: Categorized
   12 transactions as Groceries (1 rule removed)`.
A4. **Guards** (made here so B and C never edit `tests/ops`).
   - attribution-writers: add `src/lib/bulk-undo.ts#undoLastBulkAction` to `WRITERS` and
     `WRITERS_NOT_CONSULTING`. Reason: it writes back the exact value that person's own bulk change
     replaced minutes earlier, and asking `resolveAttribution` again would move rows nobody asked
     about.
   - rule-authoring-intent:
     - add `restoreExactRules` to the detector's rule-writing helpers;
     - allow `src/lib/bulk-undo.ts` with its reason (it restores the exact rules one person's bulk
       change wrote or removed, only through `restoreExactRules`);
     - extend the `src/app/(app)/transactions/actions.ts` reason to name the review-by-merchant Mark
       recurring decision (B3), which reaches `setRecurringMarks` only.

Tests (explicit `at` / `now`, March 2026):
- Categorize three MAPLE GROCER rows (two uncategorized, one Bayes guess at 0.62) with rules on,
  then undo. The categories, sources and confidence are as before, the new exact rule is gone, and
  the Bayes token counts equal a snapshot taken before the action.
- A row already `manual` Dining moved to Groceries: undo untrains Groceries and trains Dining.
- Bulk transfer over a merchant with a `not_transfer` rule: undo re-inserts that rule with its id
  and columns and removes the learned `transfer` rule.
- A teach that updated a bounded exact rule: undo writes back its category.
- A person change (including to and from Household/null) is restored.
- Recurring marks are restored.
- A loan rule link made by a re-confirm is removed, and the loan balance is as before.
- Refusals:
  - at +15:01 the undo is refused;
  - a row recategorized after the action makes it refuse with nothing changed, and so does a rule
    edited after it;
  - a recorded row deleted after the action makes it refuse.
- A second action replaces the first. Sam's action leaves Alex's record alone. A no-change action
  keeps the previous record. 2,001 rows give `too_large` and no record.
- A self viewer (Alex) undoes their own transfer change; it is refused once a row was reattributed
  to Sam.
- The undo writes exactly one audit row with the detail above.

## Lane C — transfer-pair suggestions (item 2; phase 2)

Files: `src/lib/transfer-pairs.ts` (new), `src/app/(app)/transactions/transfer-pair-actions.ts`
(new), `src/components/review/TransferPairsCard.tsx` (new); tests `tests/lib/transfer-pairs.test.ts`
(new), `tests/app/transfer-pair-actions.test.ts` (new), `tests/components/TransferPairsCard.test.tsx`
(new). C4 also edits `src/app/(app)/transactions/page.tsx`, `transactions-client.tsx` and
`tests/app/transactions-page.test.tsx`, after B is committed.

C1. **The window.** No date-window transfer logic exists. Detection is merchant-only:
   `CARD_PAYMENT_PATTERNS` and transfer rules (engine.ts ~:40, `detectTransfer` ~:136). So the window
   is the app's existing "same money, two rows" window: `DUPLICATE_WINDOW_DAYS = 3`
   (predict/constants.ts ~:94) and v1.61.0's D2, both 3 days. `TRANSFER_PAIR_WINDOW_DAYS = 3` lives
   in transfer-pairs.ts.
C2. **The suggester.** `suggestTransferPairs(viewer, { limit = 20 })` returns `[]` for a self viewer.
   `isPairCandidate(out, in, ctx)` is the one predicate. Every condition must hold:
   - `out.amountCents = -in.amountCents`, and it is not zero;
   - the two rows are on different accounts, both active and `acceptsTransactions`;
   - `|daysBetweenIso(out.date, in.date)| <= 3`;
   - neither row is split, neither is loan-linked, and neither is filed by hand to a category while
     not a transfer (`manual` and `is_transfer = 0` means the household called it spending);
   - at least one side is in the review queue (`REVIEW_WHERE`), and at least one side is not yet a
     transfer;
   - the scope rule: when either account's owner is a self-scoped member (`visibility = 'self'`,
     role member), both accounts must have that same owner. A shared account (owner null) never
     pairs with a self-scoped member's account;
   - the pair is not dismissed.

   Reads:
   1. the queue rows once;
   2. the counterpart rows with dates in `[min-3, max+3]` and amounts in the negated set
      (`transactions_date_idx`);
   3. the accounts with their owners' visibility.

   Matching is one-to-one: outgoing rows in (date, id) order each claim the nearest unclaimed
   incoming row (tie: lower id). A dismissed pair is skipped, and both of its rows stay free to pair
   with another row. Results are newest first, each side carrying `id, date, accountName,
   description, amountCents, isTransfer, personName`, plus the total count. v1.61.0's held
   set-aside rows are not transactions and never pair.
C3. **Confirm and dismiss.**
   - `confirmTransferPair({ outId, inId, viewer, at })`:
     - refuses a self viewer;
     - refuses unless `isPairCandidate` still holds: `That pair has changed since it was suggested.
       Nothing was changed.`;
     - in one db transaction, runs `setTransferFlag({ learnRule: false })` on each side not yet a
       transfer, and a split refusal refuses the whole pair.
     - No rule is saved. A pair is a transfer because of its other half, the link-driven case
       `setTransferFlag`'s docblock describes (~:1585). E-transfer descriptions are shared with
       payments to people outside the household, so a learned rule would misfile them.
   - Dismissals: settings key `transfer_pair_dismissed:<outId>:<inId>` = date, validated by a
     regex, written by `dismissTransferPair`. Each write prunes keys naming a row that no longer
     exists (the `pruneInsightDismissals` shape).
   - transfer-pair-actions.ts:
     - `confirmTransferPairAction` and `dismissTransferPairAction`: origin check first, ids parsed
       with `@/lib/zod`;
     - confirm is wrapped in A's capture/record (`transfer_pair`, `Marked 2 transactions as a
       transfer pair.`);
     - both revalidate `/transactions`, `/dashboard`, `/budgets` and `/reports`.

   Tests (Alex, Sam; chequing -500.00 on 2026-03-09):
   - window: savings +500.00 on 03-12 pairs; on 03-13 it does not;
   - 1 cent off, the same account, and an inactive account do not pair;
   - scope, with Alex self-scoped:
     - Alex chequing with Alex savings pairs;
     - Alex with Sam does not;
     - Alex with a shared account does not;
     - Sam (household) with a shared account pairs;
   - one side already a transfer is suggested, and confirm marks only the other;
   - a hand-filed Groceries row, a loan-linked row and a split row are never counterparts;
   - the one-to-one tie-break;
   - a dismissal is remembered across calls while both rows still pair elsewhere, and the prune
     works;
   - confirm writes no `merchant_rules` row, records an undo that restores both sides, and audits
     nothing until undone;
   - a stale pair is refused;
   - a self viewer is refused, and the suggester returns `[]` for them;
   - a member can confirm.
C4. **Card and mount** (mount after B is committed; re-read both files).
   - `TransferPairsCard` (`'use client'`, props only) hides itself when empty.
     - Its title is `Possible transfers (N)`.
     - Each pair has two lines (account, date, description, signed amount, and an `already a
       transfer` badge where true), then `Mark both as a transfer` and `Not a transfer`.
     - A quiet line reads `No rule is saved, so the next pair like this is suggested again.` It
       shows 20 and `N more after these are done`.
   - page.tsx, review mode only: `transferPairs = selfScopedViewer ? null : suggestTransferPairs(viewer)`.
     The client renders the card above the queue, after v1.61.0's `PossibleDuplicatesCard`, in both
     `List` and `By merchant`.
   - Tests:
     - the card's lines and buttons render, and each button posts its ids;
     - an admin sees it in review mode;
     - a self viewer's `?review=1` serializes no pair.

D1. **The formula** (pure, pace.ts).
   - `projectMonthEnd` is replaced by `checkInMonthEnd({ spentCents, dueCents, history: { cents,
     days }, daysLeft })`. It returns `max(spentCents, 0) + dueCents + everyday`, where `everyday =
     divRound(max(history.cents, 0) * daysLeft, history.days)`.
   - `daysLeft = daysInMonth - dayOfMonth`. Today counts as elapsed (MUST-8.3 kept), so the last
     day is spent plus due.
   - It returns null when `daysLeft > 0` and `history.days === 0` (no full month of history yet).
     There is no straight-line fallback and no day-7 floor for display.
   - The docblock records that v1.62.0 supersedes MUST-8.4 (display only), MUST-8.6 and MUST-16.4,
     and keeps MUST-8.3, MUST-8.5 (spend below zero counts as zero) and MUST-8.7 (spent is the
     figure already on screen).
   - constants: `CHECKIN_HISTORY_MONTHS = 3`. `PACE_MIN_DAY_OF_MONTH` stays, for alerts only.
   - window.ts: `historyMonths` takes an optional `count`.

   Tests (2026-03-07, 31 days, history days = 24 + 24 + 21 = 69):

D2. **The rest-of-month history** (history.ts, the one DB module under predict).
   `restOfMonthSpend({ targetMonth, dayOfMonth, scope, userId, excludeMerchant })`:
   - Months are `historyMonths({ count: 3 })`, clipped at `firstDataMonth`.
   - One grouped read over those months:
     - rows dated after `dayOfMonth`, by SQL on the stored date text (`cast(substr(date, 9, 2) as
       integer) > ?`);
     - `SPEND_ROW_WHERE`;
     - not paid to a bill installment (`not exists bill_installments.paid_txn_id`);
     - the scope (personal = attributed user);
     - grouped by (month, `EFFECTIVE_CATEGORY`, `normalized_merchant`) with the split joins
       `cells()` uses.
   - In memory:
     1. drop excluded merchants;
     2. apply `netSpentCents` per (month, category) cell (MUST-4.9);
     3. sum the months;
     4. roll up with the same rollup `categorySeries` uses;
     5. compute `totalCents` by `cashflowTrend`'s spend rule (income categories out, uncategorized
        money out in full).
   - It returns `{ months, daysAfter = Σ max(0, len(m) - dayOfMonth), byCategory, totalCents }`.

   This is day-aligned on purpose. It reads what was spent in the same stretch of past months, so a
   payment that always lands early in the month (rent on the 1st) adds nothing for the rest of it,
   marked or not.

   Tests:
   - With `dayOfMonth = 0` and nothing excluded, `byCategory` equals `categorySeries`' cells summed
     over the same months, and `totalCents` equals the sum of `cashflowForRange(month).spendCents`.
   - A row on day d is excluded, and a row on day d+1 is included.
   - An installment-paid row is excluded.
   - An excluded merchant is dropped.
   - The personal scope is applied.
   - Split rows count at their parts.
   - A household two months old uses two months.

## Owner decisions (defaults in force unless changed)

1. Undo covers the last bulk change per person for **15 minutes**, and refuses if anything in it was
   edited since. It covers categorize (bar, groups, confirm view, apply to all, accept all), mark
   transfer, person (bulk bar), recurring marks, merchant decisions and transfer pairs.
2. The rest-of-month part is **day-aligned**: what was spent after today's day of the month in each
   of the last 3 full months. Rent on the 1st reads right even when nobody marked it. Alternative:
   a flat daily average times days left, which needs rent marked recurring or set up as a bill.
3. The check-in shows **from the 1st** once one full month of history exists, and **nothing before
   that** (no straight-line fallback). Pace alerts still start on the 7th, now on the new figure.
4. Transfer pairs use a **3-day** window, and confirming **saves no rule**.
5. A merchant decision applies to that merchant's **queued rows only**, with Remember ticked by
   default as on the bulk Categorize bar.

## Review focus (one Opus review)

- An undo restores exactly what the action changed: rows, rule rows (ids included), Bayes counts and
  rule loan links. It refuses whole, never half, and only the person who acted can undo.
- Every bulk entry point records, and the per-row paths do not.
- Merchant decisions write through the existing bulk writers. The group set equals the header count
  and never leaves the queue or the viewer.
- The pair predicate is one function, used by both the suggester and confirm. Matching is
  one-to-one and deterministic. The self-scoped account rule holds, and confirm writes no rule.
- The check-in never counts a due bill or marked charge twice (the matcher, installment-paid rows).
  Day-aligned history at month-length edges. The person pill and self scope on every reader. The
  per-category figure is the on-screen `spentCents`.
- The alert, digest, Budgets and Dashboard all read one function.
- `REVIEW_WHERE` and its index are untouched. No migration.

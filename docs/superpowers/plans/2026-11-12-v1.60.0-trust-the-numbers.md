# Trust the numbers — Implementation Plan (v1.60.0)

**Goal:** Make every figure the app shows agree with the money that actually moved, and make the
background jobs that keep those figures safe (bank sync, nightly backup) fail loudly and cheaply
instead of silently. Bulk actions stop re-filing rows nobody can see, imports and undo say what they
will do, and the pages that run on every visit do less work for the same answer. Every item lands
with a test that fails on v1.59.1 (or, for the speed items, a before/after equality test).

**Base:** v1.59.1 (`3f65242`). Work on `main`, no branches or worktrees. Item numbers below are the
review's finding numbers (1-14), so a lane lists them out of order.

**Process (lean):** one fresh implementer per lane. Lanes A-E run in parallel; their file sets are
disjoint (listed per lane). Two steps are sequenced, not parallel: item 7e (one dashboard insertion)
runs only after Lane B is committed, and Lane F runs only after A-E have finished their test runs,
because `npm install` rewrites `node_modules` under every other lane. Implementers run the tests they
touch, `tests/ops`, and every test file that imports a module they change
(`rg -l "<module path>" tests`), and do not commit; the orchestrator commits each lane by file name
(F's commit lands before the release commit). Then ONE review over the whole range, one fix round,
then the release gate once.

## Global constraints

- PUBLIC repo: no owner name, employer, Windows paths, account names or real figures. Invent every
  fixture value (people `Alex` / `Sam`, merchants like `MAPLE GROCER`, `FUEL STOP 12`). No quotes of
  anyone in comments.
- App-only: no compose, Docker, install-script or docs-for-operators changes, and nothing the owner
  must test on a NAS. The one migration (0030, Lane E) applies on boot like every other.
- Respect self-scoped viewers (`isSelfScoped` / `ownerScope`) and non-admin members everywhere a
  number or a link is shown; reuse `listAccounts({}, viewer)`, `canActOnOwner`, `requireAdmin`.
- `'use server'` files export only async functions; every action's first statement is its origin
  check (`tests/ops/use-server-exports`, `tests/ops/server-action-origin`).
- Tests use explicit dates, never today (pass `today`/`now`, or `vi.useFakeTimers({ toFake: ['Date'] })`
  as `tests/app/dashboard.test.tsx` does). Vitest 4 + Testing Library, no jest-dom. Household dates
  come from the tz-aware helpers (`todayIso`, `monthStart`, `monthEnd`), never a UTC slice
  (`tests/ops/no-utc-date-slice`).
- One definition per rule: a figure that two pages show comes from one function. Speed items keep
  results identical; prove it with an equality test written against v1.59.1 behaviour first.
- Never `git stash`, `git checkout -- <file>` or `git restore` (CRLF rewrite breaks ops guards).
- TypeScript 6.0.3 and Next 16 stay pinned (major).

3a. **Failures cannot spend the sync allowance.** `last_sync_at` moves only on a clean run (sync.ts
   ~:271) and the 5-minute tick's due check reads only that (scheduler.ts ~:208), so one bank that
   keeps failing re-runs the sync every tick until the 20 requests are gone. Settings keys (beside
   `SETTING_AUTO_SYNC` in connection.ts) record consecutive automatic failures and the last automatic
   attempt. `autoSyncBackoffMs(failures)` = min(30 min x 2^(failures-1), 24 h). `runSimplefinTick`'s
   gate also returns while the backoff since the last attempt has not run out; `runAutoSimplefinSync`
   records the attempt before `runSync` and counts any throw (including its own errlist throw) as a
   failure; `markSynced` (a clean run, manual or automatic) resets both keys. A manual sync ignores the
   backoff. Settings, Connections shows one quiet line while backing off: `Automatic sync is waiting
   after 3 failed tries. Next try about 14:30.` Tests (explicit `now`): a persistent errlist over 24 h
   of 5-minute ticks makes at most 6 requests and leaves at least 14 of 20; the gap caps at 24 h; a
   clean run resets the count; a manual sync during backoff runs; a thrown fetch error backs off too.
7. **Backup health.**
   a. *Check each new archive before it replaces anything.* `buildArchive(target, { verify })` runs
      `verify` on the `.partial` before the rename into place. backup.ts passes `verifyBackupArchive`
      from `src/lib/backup/restore.ts` (the one bridge into `scripts/`, MUST-20.5, pinned by
      `tests/ops/restore-seams`), which calls a new alias-free `verifyArchive(artifactPath, scratchDir)`
      in `scripts/restore-core.ts`: `assertArchiveEntriesAreSafe` (reads the whole gzip stream, so a
      truncated or corrupt archive fails), extract `budget.db` only, `preflightSqliteFile` (magic bytes
      and `PRAGMA quick_check`), remove the scratch directory. A failure deletes the partial, leaves
      the previous archive at that name, and throws `The new backup failed its check: ...` into the
      existing failure path, so retention never counts or evicts in favour of a bad archive. The
      pre-upgrade backup inherits it (rewrite its "deliberately thin" docblock: VACUUM proves the
      source, the check proves what landed on disk). On-demand downloads are unchanged. Tests: a
      truncated partial and a tar with a garbage `budget.db` both fail and keep yesterday's archive;
      a good archive passes.
   b. *Remember the outcome.* `runNightlyJob`'s catch records `backup_last_failure_at` and
      `backup_last_failure_reason` (setting names in settings.ts); a success clears them. Backup age is
      the newest nightly archive's mtime (`listBackups`), which stays true after a restore.
   c. *Boot catch-up.* Pure `backupCatchUpDue(newestAt, now)`: true when there is no nightly archive or
      the newest is older than 26 h. `startScheduler` checks it once at boot and, when due and at
      least one user exists, runs `runNightlyTick` after a two-minute unref'd timer (boot is never
      blocked; `stopScheduler` clears it). Tests: 25 h no, 27 h yes, none yes, no users no; timer
      registered and cleared (fake timers); `tests/ops/scheduler-tick-guard` passes.
   d. *Health summary.* `backupHealth(now)` in backup.ts returns `{ lastBackupAt, ageHours, state:
      'ok' | 'stale' | 'failed' | 'none', failureReason }` (failed = a recorded failure newer than the
      newest archive; stale = older than 26 h). `BackupHealthLine` renders one muted line, `Last backup
      7 hours ago`, or a warning-toned one, `Last night's backup failed` / `No backup for 3 days`,
      each with a `Settings, Backups` link to `/settings/backups`. Settings, Backups shows the failure
      reason when there is one.
   e. *Dashboard (after Lane B is committed; re-read the file first).* One import and one JSX block
      under the page header, rendered only when `viewer.role === 'admin'`. Tests: admin sees it;
      member and self viewer do not.

13a. **Review count with an index.** The layout (~:29) counts `REVIEW_WHERE` (engine.ts ~:2128) on every
   navigation with no usable index. Migration 0030 adds a partial index
   `transactions_review_idx on transactions (date) where is_transfer = 0 and (category_id is null or
   categorization_source = 'bayes')`, declared in schema.ts too. SQLite uses a partial index only when
   the query's terms match its WHERE, and a bound parameter never matches a literal, so REVIEW_WHERE's
   first two terms become literal SQL identical to the index predicate (same meaning; the narrowing
   constants are unchanged). `reviewQueueCount` is wrapped in React `cache`, so the layout and the
   page share one count per request; confirm `cache` is a passthrough outside a server render (two
   calls in one test with an insert between must differ). Tests: migration-0030 asserts the index

12. **Deactivating an account keeps its past.** `netWorthOverTime` (~:335) reads only active accounts,
   so deactivating one rewrites every past month. Deactivation is a bare `is_active` flag
   (`setAccountActive`, accounts.ts :121) with no date and no audit entry, so the minimal correct rule
   needs one: migration 0030 adds nullable `accounts.deactivated_at` (YYYY-MM-DD). `setAccountActive`
   stamps the household's today on deactivation and clears it on reactivation. Backfill for accounts
   already inactive: the day after their last activity (latest snapshot date, latest transaction date,
   or created date). `netWorthOverTime` reads `listAccounts({ includeInactive: true }, viewer)` and
   counts an account in a month when it is active or `deactivated_at > monthEnd(month)`; the
   first-snapshot floor and `accountsMissing` use that month's set. Tests: snapshots Jan-Mar 2026,
   deactivated 2026-04-10, Jan-Mar unchanged and Apr on excluded; reactivated, counted again;
   migration backfill (last snapshot 2025-11-20, last transaction 2025-12-02 gives 2025-12-03; active
   accounts stay NULL), following the tests/db migration pattern (journal position, column, backfill).
5. **Goal pace on the 1st.** `computePace` (~:76, :91-92) divides by a window that includes the
   unfinished current month, so on the 1st the average drops by a third and `goal_off_pace` (keyed per
